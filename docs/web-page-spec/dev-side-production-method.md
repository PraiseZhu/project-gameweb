## 结论

开发侧的页面**也是 AI 做的**，但做法和 Gameweb 不同：

- **Gameweb**：脚本把 Figma 图层**自动转换**成页面。
- **开发侧**：AI 编程助手**看着 Figma 稿，像前端一样直接写源码**。人一轮一轮提要求，AI 一轮一轮修改。

## 证据

1. **仓库位置**：`git.xindong.com/xd-website/ai-sites/etheria/ews2026`。分组名叫 `ai-sites`。
2. **AI 工作痕迹**：README 里多处写着“Work 设置禁用了浏览器操作”“按用户要求未操作浏览器”“用户确认使用 SDK 国内 cn 分支”，都是 AI 助手在汇报。
3. **时间线**：2026-10-29 建仓，10-29 到 11-09 之间约 20 轮修改。每轮在 README 里记一节，写明日期、改了什么、怎么验证、哪些还没验。

## 制作方法

| 环节 | 开发侧的做法 |
|---|---|
| 看稿 | 用 Figma 客户端核对设计，按节点 id 对照（例如 `219:4115`、`183:7531`） |
| 切图 | Figma 客户端**原生 1× 导出**，二倍稿直接得到 2 倍图；导出时**排除文字**（manifest 记 `textsExcluded`）。部分图由用户提供（`user-provided`） |
| 写页面 | AI 直接写 HTML / CSS / JS 源码。文字一律写成 HTML 文字，不切进图里 |
| 布局 | 起初用绝对定位，10-30 专门改成“正常流”（flex/grid）：普通文字不设固定宽高；全局 `.text`、`.image` 不再默认 absolute；只有底图、装饰、皇冠、滑块这类叠加元素单独定位；结果是“正文文字无 absolute 定位” |
| 套模板 | 整屏切换照团队的 **`site-components/skills/onepage-template/SKILL.md`** 做（这个文件在开发者本机，我们手上没有） |
| 复用组件 | 页脚从 `site-components/components/site-footer/` **原字节复制**；闪烁动效复用 `website-components/components/flicker-entrance`；埋点复用 `torchlight/ss14/js/tracking.js` |
| 参照旧页 | rem 规则参照火炬 SS14；导航缩放参照 EWS2025；切屏节奏参照伊瑟官网；社媒和链接照 2025 各语言页补齐 |
| 推进顺序 | 简中 PC → 逐块细调 → 简中移动端 → 四种外语 → 动效 → 懒加载 → 页脚 → 埋点 |
| 验证 | 每轮都做两层：① 源码检查（语法、引用、唯一 ID、素材字节与尺寸）；② 真实浏览器多视口实测（1280×720 ~ 2560×1080、375×812、断点 1024/1025 往返），并用本地假数据测 0/1/5/9 条等边界。没验的项会明确写“未验收” |
| 记录 | `assets/manifest.json` 记录每张图的来源节点、尺寸、字节和校验值；README 逐轮写变更日志 |

## 对 Gameweb 的含义（留到流程讨论阶段再展开）

- 开发侧的页面结构来自“AI 理解这一屏是什么内容，再按模板和组件写出来”，而不是来自图层树。
- Figma 在开发侧只有两个用途：**当尺子**（量尺寸、字号、位置）和**当切图来源**。它不决定 DOM 结构。
- onepage-template Skill 是开发实际制作 Onepage 的规则来源，列为需要开发提供的核心资料（R1）；要核对完整 Skill、实际引用的配套文件及使用版本，再讨论 Gameweb 衔接。它不阻塞 HTML v1 定稿，但不能因此降为可选参考。三个公共组件的正式接入仍按第 6.4、17 项归开发，不因此要求 Gameweb 现在接入组件库。

## 开发侧怎么保证还原度（2026-11-11 查证）

用户提问：AI 像程序员一样看稿写代码，怎么保证完美复刻？Gameweb 靠精准的数据结构复现，开发侧靠什么？

查证结果（来源：提交版 README 逐轮记录）：

1. **数字照抄设计稿，不靠目测。** 每个尺寸都写着来自哪个节点、换算成多少。例如：主标题 130px（二倍稿）→ `.65rem`；移动选手卡按节点 `126:3659` 的 324×465 → `1.62×2.325rem`；底栏按 `221:1345`（3840×138）同步。换算规则固定为二倍稿数值 ÷ 200 = rem。
2. **图片原样导出。** 用 Figma 客户端原生 1× 导出，manifest 记录字节数和校验值，保证图和稿一模一样。
3. **浏览器量几何。** 测的是“内部是否对齐”，比如选中背景和按钮中心误差 < 0.03px、卡片组居中偏差为 0、重构前后 958 个元素位置差 < 0.1px；也会多视口检查有没有溢出。
4. **人一轮一轮看。** 约 20 轮修改，大部分由人看出问题再提出来，例如“按最新稿更新字号”“校正决赛 TAB 重叠”。

**记录缺口：** 这份 README **没有记载拿页面截图和设计稿做像素对比**。浏览器测量证明的是“页面自己对得齐”，不能证明“和设计稿一样”。和稿子是否一致，最后靠的是人眼加多轮返工。部分轮次的浏览器被禁用，README 自己也写了“页面视觉仍需浏览器验收”。

**对比此前 Gameweb 记录（不表示本轮重新核验当前实现）：**
- 数字来源：两边都来自设计稿，只是取法不同。Gameweb 由脚本整批抓取；开发侧由 AI 一个个查，再填进语义结构。
- 结构：Gameweb 照搬图层；开发侧按内容重新组织。
- 验收：Gameweb 的既有记录包含像素门；开发样本 README 没有记载像素对比。是否另有工具／报告仍需开发回答（R7），不能据此断言整个开发侧没有。

**已确认原则（README P8）：** 结构按开发侧组织，数字来自 Gameweb 清单，不许目测；还原度由 Gameweb 流程验证。2026-11-16 已明确检测工具、执行方法和阈值归流程，不作为 HTML 标准定稿前置。
