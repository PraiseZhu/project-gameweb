# 3. Gameweb 制作前：开发资料交付说明与核对要求

更新日期：2026-11-17。三份交接文件中的第 3 份，给开发提供资料的人，以及后续接手 Gameweb 的人阅读。

本文可直接交给开发：四类资料逐项写明给什么、为什么需要、设计侧可能怎样使用、已有／还缺以及怎样核对是否可用。只涉及 Gameweb 制作前的资料，不包含成品交付后开发接入和上线的工作。

## 1. 先看这次交接是为了什么

我们已经把开发提供的 ews2026 页面整理成 **HTML 交付标准 v1，标准已定稿**。下一阶段要讨论：Gameweb 怎样根据设计稿和清单，做出符合这套标准的静态 HTML 页面。

**现在向开发要资料，是为了把 Gameweb 的制作方法定清楚。** 不是让设计侧提前处理后台、正式组件接入或上线，也不是要求开发重新制作一套资料。

当前情况：

- **已经有**：ews2026 的 HTML、CSS、JS、素材目录、字体目录和 manifest，可供参考；本地基础提交是 39f9d71，工作区还包含后续未提交修改。
- **已经定**：成品的结构、样式、交互、素材和验收要求，详见 [HTML v1 完整规范](html-standard-checklist.md)。与原样本一致和不同的地方放在本文附录。
- **还没完成**：Onepage Skill 等待提供资料的收集、Gameweb 流程方案及实现、实际页面验收。不能把已有样本当成所有规则和工具都已拿齐。

下面四类就是当前资料范围。已有的只确认版本、补缺件；没有现成文档的可以简单说明，不要求新写长报告。

## 2. 开发要提供什么，我们为什么要、怎样用

### 2.1 Onepage 制作 Skill——弄清开发做这种页面的原始规则

**请开发给什么**

制作 ews2026 时实际使用的 **site-components/skills/onepage-template/ 完整目录**：SKILL.md、它实际引用的模板／脚本／参考文件（如有），以及使用的版本或提交号。给目录包，或可读取的仓库位置和版本都可以；只给 SKILL.md 的截图不够，里面引用的文件也需要能读到。

**我们为什么要**

开发的 README 明确写了 Onepage 行为参考这份 Skill。现有 HTML 只能告诉我们“这一页最后做成了什么”，Skill 才能说明开发原本怎样组织整屏切换页、哪些规则是固定的、哪些可以随项目变化，避免继续只靠一个成品反推。

**拿到后怎么用**

先读 Skill 和配套文件，对照已经定好的 HTML v1，找出可复用的模板与行为规则、已有样本没有说明的约束。再把结论用于后续“ready 清单怎样生成静态 DOM、交互和适配代码”的流程讨论。设计内容和几何仍来自清单，不改成让 AI 看图猜；Skill 也不会自动覆盖已经确认的 v1 调整。

**现在已有／还缺**

已知准确的引用路径，但完整 Skill 尚未取得。拿到资料不代表已经安装、执行或决定直接使用它。

**怎样判断这份资料交得合格**

- 交的是可读取的 Skill 文件和真实目录，不只是名称、截图或开发电脑上的绝对路径。
- SKILL.md 引用的必要模板／脚本／参考文件能找到；外部依赖有明确位置和取得方式。确实没有配套文件时，说明没有即可，不要求额外创造。
- 能确定是哪一个版本、是否为制作 ews2026 当时使用的版本；如果给的是更新版，说明与样本所用版本的区别。
- 接收后能读懂它的输入、产出和使用前提。缺文件或引用失效时列明待补，不因收到一个 SKILL.md 就算完整。

这里核对的是资料完整和可读，不在接收时自动安装依赖、执行脚本或改动现有项目。

### 2.2 制作页面直接用的模板、动效和资源——让 Gameweb 有可用的制作材料

**请开发给什么**

只给这次页面制作实际要复用的文件及必要说明。例如：

- 页面里的闪烁动效样式及其用法，来源线索为 website-components/components/flicker-entrance/。
- Onepage Skill 或制作模板引用、但现有工程没有的配套文件；已在上一项提供的不再重复要。
- 如果继续使用开发样本里的字体，补缺失的字体来源／许可说明。
- 确认我们持有的 ews2026 工程对应哪个可参考版本；若缺必要文件，只补那些缺件。

**我们为什么要**

这些会影响 Gameweb 最终生成的页面：例如缺闪烁样式就无法按已定方式做开场效果，缺指定字体就无法按稿显示文字。我们要的是制作所需的文件和用法，不是整个公司的组件库。

**拿到后怎么用**

在流程讨论中确认哪些文件可以直接复用、哪些要随页面输出，并核对它们与已定动效／字体规则是否一致。后续获准制作时，再把实际使用的样式和字体纳入页面目录，保留来源记录，用最终文件检查画面效果。原始素材的尺寸和位置仍按设计清单，不靠这些参考文件补画设计。

**现在已有／还缺**

本地已有 flicker-entrance.css、页面样式、素材及字体目录。样本闪烁只复用了 CSS，没有加载该组件 JS；不用为此索要或接入整套组件。需要的是所用版本／用法、实际依赖缺件，以及选用字体缺失的来源说明。

正式页脚、背景视频播放器、埋点 SDK 及其源库不属于这项当前素材请求；这些由开发接手后接入，Gameweb 只按已定标准预留入口。

**怎样判断这些素材交得合格**

- 交付的是制作实际需要的原文件，不是效果截图；文件可以打开或解析，内部资源引用没有缺件。现有工程中已具备的，可直接指出对应文件与版本。
- 动效样式附最简用法：应用在哪个元素、依赖哪些文件或状态、如何触发。已有说明可以直接提供，不要求重写组件文档。
- 实际使用的字体有可读取文件，以及来源／许可说明；缺失只补相关字体，不要求提供所有公司字体。
- 标明文件是否改过、适用哪个样本／版本；没有实际使用的组件文件不为了“完整”强行加入。

接收方据此登记“可用于哪一块页面、还缺什么”。能读文件不代表效果已经通过浏览器验证，后续制作仍需按 v1 检查。

### 2.3 页面字段说明和 JSON 样例——让 Gameweb 知道数据怎样变成页面内容

**请开发给什么**

一份现有字段说明和能对应起来的 JSON 样例，说明：

- 字段叫什么、是文字／数字／图片，还是列表、开关。
- 字段对应页面的哪类内容，列表如何嵌套，语言如何区分。
- 没有值、没有列表内容或开关关闭时是什么意思；如有限制，说明允许的数量和类型。
- 有现成字段命名规范一并提供；如果后台能力会限制页面准备哪些字段，只说明这项具体限制。

样例用虚构或脱敏内容即可，不需要正式名单、比分、真实接口地址或后台账号。页面自身是否需要动态数据，仍按实际项目范围确定。

**我们为什么要**

设计稿只画出某一刻的样子，不能告诉 Gameweb 哪些内容以后会变、哪些是重复列表、哪些控制整块显示。没有这些说明，生成器就不知道该把数据填到哪里，也不知道条数变化后该怎样分页和显示空状态。

**拿到后怎么用**

用字段说明核对设计阶段明确的内容与数据关系，讨论清单需要怎样记录；后续再据此生成 HTML 中的重复项模板，以及读取 JSON、填文字／图片、处理列表／开关和语言的页面代码。用示例数据检查空列表、单页、多页、字段缺省等已定情况，避免测试时依赖真实后台。

比如“选手列表”是一组重复数据，Gameweb 就需要生成对应卡片并按已定轮播规则分页；控制某屏的开关关闭时，该屏及对应导航一起隐藏。这个说明决定的是页面代码行为，不是怎样管理后台。

**现在已有／还缺**

已有样本字段观察和页面读取代码；开发确认的字段约定、样例及命名说明仍待补。新页面若没有开发既定字段，按已确认的“设计稿先定”方向准备字段，再核对实际限制，不能把“还没给”当作“后台一定支持”。

后台入口、权限申请、操作手册、发布流程不在本次资料范围内。正式数据和接口接通留开发后续处理。

**怎样判断数据资料交得合格**

- JSON 是可解析的文件，示例值与字段说明的名称、类型和嵌套层级一致，不只给一张后台截图。
- 说明能区分固定值、重复列表、显隐开关和语言内容，并能知道它们对应页面哪类内容。
- 对实际存在的空值、空列表、缺字段、无当前语言内容等情况，说明其含义和已有约定；有条数或类型限制则写明。未定的部分明确标出来，不伪装成已经支持。
- 样例只需足以说明结构，后续空列表、单页、多页等测试数据可由 Gameweb 按约定构造，不要求开发准备整套测试报告。
- 有现成字段命名规则就一起给；没有则明确没有，按已经确认的设计字段方向继续对齐。样例不依赖真实接口可访问，也不夹带生产账号或密钥。

接收方先比对“说明与样例是否一致、是否足以写出页面读取逻辑”；不把后台已经建好或正式数据已经发布当作资料通过条件。

### 2.4 已有制作和验收方法／要求——让 Gameweb 按同样的尺度取数和检查

**请开发给什么**

现有的简短说明、脚本或文档即可：

- 用什么工具读取 Figma 节点数值、怎样导图，尤其是导出范围、倍率和文字处理。
- 怎样检查页面还原度和交互，已有的检查工具、用例或结果记录。
- 如果已有图片／字体、视频／包体积、浏览器／性能要求，给对应规则和适用条件；没有就说明没有。

**我们为什么要**

同一张设计稿，如果取数、切图边界或验收尺度不同，最后页面可能不一致。这些资料用来理解开发实际采用的方法，避免 Gameweb 漏掉已存在的要求或重复造一套工具。

**拿到后怎么用**

对照 Gameweb 现有的清单抽取、素材导出、编码与页面检查能力，找出可复用的步骤和缺口，记入后续流程待讨论事项。比如导出倍率影响源图检查，验收用例影响测试数据准备。具体怎么选工具、怎样校准阈值仍在流程阶段决定；开发没有正式标准时，不凭空新增数字。

**现在已有／还缺**

已有开发提交版 README 中的部分制作与验收记录，但没有完整说明具体取数工具等细节；也没有取得统一的正式图片／视频／性能标准。现在的 WebP 参数已按 v1 确定，15 MB 单视频／120 MB 整包仍是暂定建议。新资料如与已定要求冲突，列清差异再讨论修订，不自动替换。

**怎样判断方法和要求说明够用**

- 取数／导图说明能定位使用的工具及其版本或环境，并说明节点、范围、倍率和文字处理这些影响结果的步骤；现成文档、脚本或简短操作说明均可。
- 验收依据写清检查对象与条件，例如参考设计、端别、语言、视口、静态状态，以及哪些做过、哪些未验证；不能只给一句“验过了”。已有记录已说明的内容无需重复写。
- 有数值要求时说明单位、适用范围和测量条件，并区分“正式要求”“样本做法”“暂定建议”；没有正式标准就注明暂无，不要求开发临时编造。
- 接收后能判断该资料用于哪个 Gameweb 制作／检查环节；仍不能确定的地方列出具体问题，后续再讨论，不自动提高或降低 v1 要求。

## 3. 提供方式与接收核对

### 3.1 开发怎样交，接手人怎样收

四类资料可以放在一个文件夹／压缩包里，也可以给可访问的仓库链接和版本；不要求采用特定新系统。文件旁附一份简短说明，写清下面几件事即可：

- 这是哪一类资料、用于哪个页面或模板。
- 文件／目录位置和对应版本；哪些直接复用我们已有的 ews2026 工程。
- 必要依赖和最简单的使用方式；与样本版本不同的地方。
- 哪些已经提供、哪些还没有，以及没有的原因。

只给无法访问的链接、提供者电脑上的路径，或有说明却找不到必要文件，均记为待补；不让接手人自行猜缺失内容。

### 3.2 按什么结论接收

| 接收结论 | 含义 |
|---|---|
| 已收到，可用于后续流程讨论 | 文件和说明可读、必要引用齐全、版本明确，足以说明本项制作问题；不等于代码／页面已验收 |
| 待补齐 | 缺文件、依赖、版本、字段含义或适用条件；具体列出缺什么、影响哪一步，不能只写“资料不全” |
| 本项目不涉及／暂无现成资料 | 只用于确实不适用的资源或没有现成的标准／记录，并说明原因；Onepage 完整 Skill 尚未给到仍记为待提供，不能用“暂无”当作已交齐 |

每一类分别记录结论，不能因为 Skill 已收到就把 JSON 或字体等其他资料也标成齐全。**本文件列的是接收要求；实际是否符合，要在开发提供后逐项核对，不提前承诺资料已合格。**

## 4. 接手后怎样消化这些资料

以下只是资料的接收与消化方式，不代表 Gameweb 的制作流程已经定好或获准开工：

1. **按上面四类收资料**：记录实际文件／链接、版本和还缺什么；已有的别重复索取，没有的让开发说明。
2. **核对它解决哪个制作问题**：分别落到 Onepage 生成规则、实际资源复用、页面数据处理、取数与验收方法。不能只收下一堆文件就算消化完成。
3. **把结论写回已有流程待办**：Skill 对应 D1，动效／资源对应 D4、D5、F17，数据对应 F6、D3，方法与检查对应 C4、C5、D6。标明“可复用／仍缺信息／与 v1 有差异”，由后续讨论确定具体做法。
4. **遇到缺口只问具体缺口**：例如生成接入口确实缺一个参数含义，就补该说明；不要顺势索取整个正式组件库、后台管理资料或上线配置。

接手人可以在收集这些资料的同时继续 [Gameweb 流程讨论](gameweb-workflow-discussion.md)，先梳理各步输入／输出和已知缺口；涉及模板复用、字段约定、资源接合或检查实现时，取得对应资料再核对定案。不能把全部资料齐全当成开始讨论的统一前置，也不能猜缺失内容。资料收到不代表现有工具已支持、页面已验收，或获准安装／运行外部 Skill。

## 5. 哪些东西不在本次交接请求里

后台管理入口、账号／权限、后台配置与发布操作，正式页脚／背景视频／埋点组件及生产参数，以及域名、SEO／分享、真实业务数据、部署／缓存，均留开发在接手成品后处理。设计侧需要的是符合规范的静态页面和已定接入口。

完整成品要求看 [HTML v1](html-standard-checklist.md)，向开发发送短清单时用 [四类资料清单](dev-requests.md)。历史 R 编号只在 [核对记录](coverage-audit.md) 中追溯，不再整表索取。

## 附录 B：v1 相对样本的已确认变化
