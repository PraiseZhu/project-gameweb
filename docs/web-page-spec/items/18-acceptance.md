# 第 18 项：验收标准

状态：✅ v1 成品验收要求已定稿（2026-11-16）。视觉、内容完整性、交互双层验收的结果要求已定；执行方案、工具和像素阈值归 Gameweb 流程，不作为定稿前置。

## 已定边界，不重复确认

- Gameweb／设计侧交付符合开发规范、可直接部署的静态 DOM HTML 页面／目录；只复核交付包，开发接手后的上线流程不在本阶段内（17.0、17.10）。
- 结构按开发侧组织，页面数值来自清单；还原度由 Gameweb 验收流程检查，具体截图比较方法归流程，不靠目测生成数据（P8）。
- 视口及 1024／1025 分界往返沿用第 7 项，多语言验收沿用第 10 项，不重定一套设备或语言清单。
- HTML 标准 v1 已定稿，素材与整页检查、检查器校准归 Gameweb 流程（P5）；具体页面仍须通过已定内容、字体、结构和交互验收。标准定稿不代表实际验收完成。

## 18.1 视觉还原要求（✅ 已定；具体检测方案归流程）

### 开发侧与 Gameweb 的现状

- 当前已读的开发侧 ews2026 README 记录源码／资源检查、浏览器布局和交互检查，以及人工反馈后的调整；没有提供统一的“还原度百分比”或对设计稿像素差异的合格线。几何测量的个别样本值不能直接当作整页视觉评分标准。
- Gameweb 当前已有停 1 像素工具，会逐屏比较页面截图与 Figma 分区图，生成 baseline／demo／diff；代码默认有差异比例和色差参数。它们是当前流程实现事实，不是本 HTML 规范现在批准的交付阈值。
- 截图方式、比较引擎、缩放、字体、遮罩、设备组合、差异阈值和校准样本都属于 Gameweb 流程阶段；本项不在 HTML 清单里锁定这些参数。
- 任何流程默认值都不能解释成“视觉相似度百分比”，也不能用整屏差异替代缺字、错图、字体和内容完整性检查。
- 本轮只读取代码与既有证据记录，没有截图、跑真稿像素门或进行阈值校准。

### 已定结果要求与流程边界

**HTML 页面视觉应与对应设计稿一致，并通过还原度检查；具体怎么截、怎么比、用什么阈值由 Gameweb 流程阶段确定。**

- 流程阶段如采用逐屏截图，应查看结果与差异图，不用全页平均分盖过某一屏的问题；源码读取或单元测试不代替实际页面截图。
- 缺字、错图、字体不对、内容溢出等仍按已有内容／字体／布局要求检查，不因总差异比例低于 6% 就豁免。
- 比较前须明确参考稿、语言、视口和静态状态；无对应参考的情况不伪造像素通过，具体跨语言与多视口验收方法后续讨论。
- 缺基准、未执行或读取失败不记为通过；工具历史跳过配置是否保留，属于流程阶段处理，不自动写入 HTML 标准。
- 上述检测注意事项留作流程参考，不要求完成校准才能确定 HTML 标准；机器通过不等于所有交互、最终人工验收或上线通过。第 13 项逐图画质检查仍是另一项，不借用整屏差异比例替代。

## 18.2 内容完整性（✅ 已定 2026-11-16）

交付前检查页面有没有漏内容。

已定范围：

- 设计稿里的屏、模块、标题、正文、按钮和素材都不能漏；页面结构要和约定范围一致。
- 本次约定的语言集合结构齐全，对应语言的文案、带语言素材和字体按第 10、11、13 项检查。语言数量由页面范围／需求确定，不固定为 5 种；单语只验该语言，多语逐一验实际需要的语言，不因其他语言缺席判失败。
- `unknown`、缺图、缺字、漏模块、资源引用缺失不能通过；清单和交付目录对不上时不能交给开发。
- “待公布”等占位只在已经定义的后台无数据状态下使用；不能用示例姓名、示例比分或临时占位冒充完成。
- 真实名单、比分、新闻等业务内容是否正确由需求方验收；Gameweb 检查数据能否按既定规则读取和显示，不判断业务真实性（17.3b）。

检查分工：

- 机器核对 inventory／HTML／manifest／资源引用、语言入口和必需节点是否齐全。
- 人工核对文字、语言、空状态、占位状态和页面画面，确认不漏、不串语言。
- 内容完整性独立于像素门；像素差异低于 6% 不能豁免漏字、错图或缺模块。

## 18.3 交互验收范围与双层检查（✅ 已定 2026-11-16）

**2026-11-20 补充动画送验条件：实现动画的代码必须符合开发侧页面代码规范，效果参数后续可调。** 按[HTML最终规范第4/9/11.1节](../html-standard-checklist.md)检查原生实现、依赖、CSS/JS组织、命名/状态分工和变量管理，并验证正常页内功能。实际代码不合规或必需检查未运行均不能通过；不以旧时长、位移、曲线或节奏表作为冻结效果的门槛，不把效果待调整混同于代码违规。以下功能和双层验收分工保持不变。

本条讨论如何确认已有功能真的可用，不重新规定按钮、轮播或弹窗行为，也不为验收补做设计稿没有的模块。

**2026-11-16 收敛：这里是 HTML 成品验收标准，不是 Gameweb 制作流程。保留“机器白盒先通过，人工黑盒再通过”的结果要求；如何补交互信息、如何接线、由哪个界面或工具执行，留到 Gameweb 流程讨论，当前暂停扩展。**

开发侧参考：ews2026 的提交版 README 记录了浏览器实际操作导航、TAB、轮播、菜单和弹层、键盘与拖动，以及用隔离测试数据验证空列表、单页、多页、末页不足一页等情况；未做的部分明确记为未验收。本规范已改过的规则仍以用户已定条款为准，例如第 9 项的循环方式、空状态和分页规则，不回退到开发样本的旧行为。

已定验收范围：

- **按钮和切换目标**：对本次页面实际提供且要求启用的按钮逐个操作，核对触发的动作和目标是否正确；不能只因有点击效果或出现高亮就算通过。
- **切屏、TAB 和轮播**：核对切到正确内容、选中状态和指示一致；有可变条数的列表时，用隔离测试数据覆盖 0 条、够一页、多页及末页不足一页，预期结果按第 8、9 项既定规则。
- **弹层与菜单**：核对打开、关闭、Esc、焦点进出及已有互斥规则；不要求所有弹层都额外支持规范未规定的关闭方式。
- **连续操作和窗口变化**：核对已有规则要求的快速重复操作、缩放／断点切换时状态保留、减少动画处理，避免卡在半途；不新定时长或手势阈值。
- **范围**：只验本次实际语言集合、端别和功能，适用视口沿用第 7 项；单语不补其他语言，无轮播的页面不增加轮播测试。

两道验收必须按顺序通过：

1. **机器白盒验收**：交付页面中的动作、目标、关系和状态接线须与已明确的交互要求一致；`data-*` 标记和已知目标有效，无重复 ID、丢失本地资源或未解决关系，适用数据状态符合已定规则。信息缺失或目标有歧义不能通过。正式外链／线上服务的可达性仍按第 17 项归开发后续，不因未填正式网址而扩大 Gameweb 验收范围。
2. **人工黑盒验收**：在实际页面中操作已有按钮、切屏、TAB、轮播、弹层、键盘和适用的窗口变化，检查画面结果、焦点、提示和状态是否正确。

机器白盒通过不等于页面体验正确；人工黑盒通过也不能替代交互关系缺失的机器失败。两道都通过，才算交互验收通过。

边界：

- 对应交互有错误、目标不明确或未实际验证时，不能标为通过；不靠 AI 猜接线，也不以人工点起来正常替代白盒缺失。17.7b／F1 保留信息待补状态；怎样补、放在哪一步不在本章决定。
- 语言展示仍只用 QA 外壳切换，本体语言菜单只按既定要求验外观／开合，不新增语言预览跳转（17.3a）。
- 正式网址、正式接口、真实业务数据和公共组件的正式接入仍按第 17 项归开发后续；交付阶段检查已定入口、读取／展示能力和缺省处理，不要求现在访问正式服务。
- 交互验收独立于像素对比和内容数量核对；截图相似不证明按钮操作正确。机器先验关系、人工再验操作的分工已定；执行工具、操作入口和实现步骤留到流程阶段。
