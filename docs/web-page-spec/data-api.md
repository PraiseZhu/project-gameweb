# 接口数据是什么、从哪来（2026-11-12 查证）

> 本文是数据来源及前期流程讨论的补充材料。HTML 交付标准 v1 已定稿；成品的数据读取、显示和分工以第 6、10、12、17 项为准。命名写法、字段表生成及后台能力核实归后续流程／开发衔接，不作为定稿前置。本文的请求和代码观察均为注明日期的历史证据，本轮未重新请求正式接口。

## 是什么

一个放在公司 CDN 上的 JSON 文件：`https://website.xdcdn.net/form/website/ews2026/K7M2X9B4Q6.json`。

页面打开时，`main.js` 会去读这个文件，把里面的选手名、比分、签表、视频等内容填进页面。读不到时（文件还没发布，或请求失败），页面显示“待公布”。

2026-11-12 实际请求：HTTP 200，约 13.8KB，已经有数据。

## 里面有什么（2026-11-12 实测结构）

| 字段 | 内容 | 页面上对应哪里 | 会不会增减 |
|---|---|---|---|
| `regional_qualifier` | 3 个赛区（cn / global / asia）× 4 组（a～d），每组一个选手列表：`user_name`、`score`、`silver_show` | 第 3 屏“区域赛果”的排行榜 | 会：每组人数不同（实测 2～6 人），页面最多显示 6 行；0～3 人时换短卡 |
| `schedule.online` | 线上赛 16 强 / 8 强 / 4 强的选手名 | 第 4 屏“决赛赛果”线上签表 | 不会：槽位固定，数量为 16 / 8 / 4 |
| `schedule.offline` | 线下胜者组、败者组的半决赛 / 决赛 / 冠军 | 第 4 屏线下签表 | 不会：槽位固定 |
| `schedule.championship` | 总冠军 | 第 4 屏最右侧 | 不会 |
| `player_list` | 晋级选手：`user_name`、`region`、`user_portrait`（头像图片） | 第 5 屏“晋级名单”轮播 | 会：实测 16 人，每页 4 人 |
| `news_list` | 视频新闻：`date`，以及按语言分开的 `title`、`desc`、`cover`、`video_link` | 第 6 屏“赛事视频”轮播 | 会：实测 3 条；缺当前语言的条目会被隐藏 |
| `is_jssg_visible` | 开关 | 是否显示第 4 屏“决赛赛果”及其导航按钮 | 会：整屏显示或隐藏；实测为 false |
| `is_news_visible` | 开关 | 是否显示第 6 屏“赛事视频”及其导航按钮 | 会：实测为 false |

## 从哪来（推断，待开发侧确认）

- 地址路径是 `form/website/...`，图片字段带 `storage: "oss"`、`originalFormat` 等上传信息，看起来是**运营在公司官网后台的表单系统里填写，发布后生成到 CDN 的 JSON**。
- 页面只负责读取，不负责写入。
- 谁在维护、后台在哪、字段能不能改，都需要开发侧确认（见 dev-requests R8、R9）。

## 和设计稿的关系

- 设计稿上画的选手名、比分是**示例**。上线时这些位置由接口填写，示例内容不能上线（G6）。
- 设计稿画了几张卡，不代表实际会有几张。实际数量以接口为准，所以这些组必须用自动布局（G4）。

## 只拿到一份设计稿时，怎么判断什么是接口（2026-11-12）

**结论：单看设计稿判断不出来。** 哪些内容走接口，是业务决定，不是视觉特征决定。

- **“接口内容”的定义**：页面上线以后还会变、由运营在后台改、不用改代码就能更新的内容。比如赛果、名单、视频、某一屏开不开。
- 设计稿只是某一时刻的画面。稿上的“我爱犀牛 4 分”和“赛事信息”在图层上都是文字，看不出哪个以后会变。
- 可以拿来**猜**的线索有：内容是示例或占位文字；成组重复；属于赛果、名单类内容。但这些都是猜。按已定原则（G1～G3：写进规范，不靠 AI 判断），不能拿猜的结果当依据。
- **开发侧是怎么知道的**：不是看稿看出来的，是先拿到了数据约定。README 2026-10-30 那一节直接写着“页面初始化时读取赛事 JSON……直接使用根对象中的 `regional_qualifier`、`schedule`、`player_list`、`news_list`”。字段是业务方给的，开发照着接。

**接口内容需要明确来源。** 以下为历史方案比较，2026-11-12 已选方式一；具体拼写仍留 F6：
- **方式一：设计稿命名标记（推荐）**。设计师或需求方在稿上把接口内容标出来，并写明对应哪个字段。例如组名标 `data/player_list`，文字标 `data/user_name`。没有标记的一律当固定内容。机器能直接读，和 G1～G3 一样写进命名规范。
- **方式二：单独交一份数据说明**。和设计稿一起交，列出字段和页面位置的对应关系。设计稿不用改，但要多维护一份文件，两边容易对不上。

无论选哪种，都要满足两条：
- 字段名和接口里的字段名**一字不差**；
- 有接口标记、但接口里找不到对应字段的，或者接口里有字段、稿上没有标记的，机器都要停下来上报。

### 已定：用方式一，在设计稿命名里标（2026-11-12）

### 标到什么粒度（✅ 已定 2026-11-12：分开关、列表、字段三层，各标在离内容最近的图层上）

按本页实际数据看，标记**只标在一个模块上**和**只标在一个元素上**都不够，需要分三层：

| 层 | 标在哪 | 本页例子 | 标了以后网页怎么做 |
|---|---|---|---|
| ① 开关层 | 整屏或整个模块的外层组 | 第 4 屏 → `is_jssg_visible`；第 6 屏 → `is_news_visible` | 开关为 false 时整屏隐藏，导航按钮一起隐藏 |
| ② 列表层 | 装重复项的容器，以及其中一个样板项（G2 重复项标记） | 晋级名单容器 → `player_list`，选手卡 → 重复项；排行榜每组 → `regional_qualifier.cn.a` 等，行 → 重复项 | 按接口条数生成，不足时自动补位（G4 自动布局） |
| ③ 字段层 | 样板项里具体的文字或图片元素 | 选手卡里的名字 → `user_name`、赛区 → `region`、头像 → `user_portrait`；排行行里的名字 → `user_name`、分数 → `score` | 用接口值替换稿上的示例 |

另外两种情况：
- **状态字段**：`silver_show` 控制银冠显示，并把行底图换成银色。标在银冠和银色底图这两个元素上，写明“由哪个字段控制显隐或切换”。
- **签表这种固定槽位**：`schedule.online.roundOf16` 有 16 个固定格子，不增减，但内容来自接口。每轮的容器标列表层，格子里的名字标字段层；不需要自动布局（数量固定）。

已定约束：
- 三层各标各的。每个标记都**标在离内容最近的那个图层上**。
- 字段名写**相对路径**：子层只写自己的字段名（`user_name`），完整路径由外层拼出（`player_list[].user_name`）。设计师不用写长路径。
- 没有任何标记的图层，一律当固定内容。
- 具体写法（前缀叫什么、分隔符用什么）放到修改命名规范时再定（见 README F6）。

### 具体写法什么时候定（✅ 已定 2026-11-12：现在只定两条约束——复用现有三种写法、字段名与接口一字不差；具体拼写和模块名、重复项一起，等改命名规范时再定，见 F6）

现行命名规范（`standards/figma-naming/spec/naming-spec.md`）里已经有三种写法：
- **前缀** `xxx/`：例如 `img/`、`btn/`、`sec/`、`dyn/`；
- **方括号标记** `[xxx]`：目前只有 `[replaceable]`；
- **参数** `@key=value`：例如 `@link=<key>`（“URL 在配置里，不写死在稿里”，和接口标记的思路相同）、`@go=`、`@sec=N`、`@from=N`、`@lang=`。

另外，`naming-spec.md` 目前有 22 行未提交的改动，`[replaceable]` 也在另一个会话里调整（F4）。

已定约束与流程待办：
- **现在只定约束**：接口标记必须复用现有的三种写法之一，不另造新语法；字段名必须和接口里的一字不差。
- **具体拼写**（例如是否用 `@data=player_list`）等到改命名规范时，和模块名（F1）、重复项（F2）、可选模块一起统一设计，避免几套新标记互相冲突。

## 能改字段的后台在哪（2026-11-12 查证）

**能确认的：**
- 数据文件放在阿里云 OSS 上，通过公司 CDN `website.xdcdn.net` 对外提供。响应头有 `x-oss-*`，`last-modified` 是 2026-11-09 08:39 GMT，说明有人在 11-09 更新过它。
- 文件名 `K7M2X9B4Q6` 是一串随机编号，看起来像某个后台系统自动生成的表单 ID。
- 同一路径下还有页脚配置 `form/website/common-config/common_236627.json`。页脚组件从这里读取协议、备案、社媒，说明公司官网有一套统一的“表单/配置后台”，按 app 或活动出数据文件。

**不知道的：**
- 后台叫什么、网址是什么、谁有权限、怎么新建一个活动的表单、表单里的字段由谁定义。仓库和本机都没找到线索。已加入 dev-requests R10。

**需要纠正的一个预期：** 现在这一页，**不是所有内容都能在后台改**。
- 能在后台改的只有接口里的 8 个字段：赛果、签表、晋级名单、视频列表，以及两个屏的开关。
- 赛程日期（11/07 - 11/08）、奖金金额（$30000）、标题、导航文字等，开发侧都**直接写在 HTML 里**。要改只能改代码。
- 也就是说，“哪些内容放进后台可改”是做页前要定的范围，不是自动全有。

### 后台可改范围（✅ 已定 2026-11-12：选 B，放宽）

- 除了赛事数据（赛果、名单、视频、开关），**运营常改的文字和信息也放进后台**，例如日期、奖金、标题。
- 具体放哪些字段，每个页面按实际情况定。**在设计稿阶段，由设计或需求方用字段命名标好**（即三层标记中的字段层）。稿上标了字段的，就进后台；没标的，是固定内容。
- 这一条是**在开发侧基础上的扩展**：开发侧把日期、奖金、标题直接写死在 HTML 里。
- 前提：后台里要能为这些字段建对应的输入项（依赖 R10）。

### 后台读不到时页面显示什么（✅ 已定 2026-11-12）

和已定规则 1.2（内容直接写在网页文件里）结合起来，建议：
- 网页文件里**照样写上设计稿上的当前值**，作为默认内容。这样搜索引擎能抓到，后台挂了页面也不空。
- 页面打开后再读后台：读到了就用后台的值替换，读不到就保留默认值。
- 例外：赛果、名单这类**示例数据**不能当默认值上线（G6），默认显示“待公布”。
- 多语言：后台字段要按语言分别填（和现在 `news_list` 按 `zh_CN`、`en_US` 等分开存的方式一样），每种语言的网页文件写各自语言的默认值。

用户确认：读不到就继续用页面本身的内容。说明：网页文件和后台数据是两个独立的文件，页面打开后要再通过网络去取后台数据。网络断了、CDN 出问题、数据还没发布，都会取不到，这时就显示网页里自带的内容。

已知风险（留到 Gameweb 流程及开发维护衔接处理，不影响标准定稿）：后台改过的内容如果没同步回网页文件，取不到后台数据时会显示旧值，例如后台已改成 12/20，网页里还是 11/07。

## 后台到底是“覆盖”还是“直接替换”（2026-11-12 查证；✅ 已定选 A 覆盖）

**现在的真实情况是“覆盖”，而且是在访客的浏览器里覆盖。** 后台从来没有改过页面文件本身。

证据：
- `cn.html` 里搜不到任何真实选手名（“我爱犀牛”“二月晴朗”0 处），“待公布”出现了 74 处。服务器上的页面文件一直是占位内容。
- `main.js:1499` 在页面打开后才去请求 `fetch(tournamentUrl + ?t=时间戳)`；`main.js:1298-1299`、`1318`、`1366` 用 `textContent = …` 把接口里的名字、分数写到页面上。
- 开发侧 README：“JSON 更新后刷新页面生效”“发布或更新后刷新页面读取”。
- 后台改的只是那个 JSON 文件（11-09 更新过），页面文件不变。

带来的结果：
- 访客看到的是：先出现“待公布”，接口取回来后变成真实名字。
- 搜索引擎和“查看源代码”看到的是“待公布”。
- 接口取不到时，访客一直看到“待公布”。

**两种模式：**
- **覆盖（现状）**：页面文件不变，打开时去取后台数据，在浏览器里替换显示。不需要任何发布流程，后台改完刷新就生效。
- **直接替换**：后台点“发布”后，系统把新内容写进页面文件，再重新上传。页面文件本身就是最新的，不存在“取不到”和“显示旧值”（C2）的问题。但需要一条“后台发布 → 重新生成页面 → 上传”的流程，目前没有看到这条流程存在。

**已定（2026-11-12）：选 A，覆盖**，与开发侧一致。页面文件里写默认内容；打开后从后台取数据，在浏览器里替换显示；取不到就用页面自带内容（示例数据显示“待公布”）。C2（默认值过期）作为已知风险保留。

## 接口标记谁来提供（✅ 暂定 2026-11-12：A 设计稿先定）

已定的部分（见“后台可改范围”）：在设计稿阶段，由设计或需求方用字段命名标好。拆开来看有三件事：

| 事 | 谁 |
|---|---|
| 决定哪些内容要能在后台改 | **需求方 / 运营**（业务决定） |
| 把标记写进 Figma 图层名 | **设计师** |
| 在后台建对应的输入项 | 管后台的人（未知，见 R10） |

关键是**字段名以谁为准**，因为两边必须一字不差：
- **A. 设计稿先定（推荐）**：需求方说要改哪些，设计师在稿上起字段名；出清单时自动汇总一张“字段表”，后台照着这张表建输入项。源头只有设计稿一处，和“设计稿是唯一源头”一致。前提是后台能按任意字段名新建表单（待 R10 确认）。
- **B. 后台先定**：后台先把表单建好，设计师照抄字段名。适合后台字段已经固定、不能随便加的情况。开发侧这页（EWS2026）实际是这种：JSON 结构先定，页面照着接。

### 开发侧这页的字段是谁定的（用户追问，2026-11-12 查证）

**用的字段**（实测 JSON 根对象）：
- `regional_qualifier.{cn|global|asia}.{a|b|c|d}[]`，每项含 `user_name`、`score`、`silver_show`；
- `schedule.online.{roundOf16|quarter_final|semi_final}[].user_name`；
- `schedule.offline.{upper_bracket|lower_bracket}.{semi_final|final|champion}`；
- `schedule.championship.user_name`；
- `player_list[]`，每项含 `user_name`、`region`、`user_portrait`（图片对象）；
- `news_list[]`，每项含 `date`，以及 `news.{zh_CN|en_US|zh_TW|ja_JP|ko_KR}`，后者含 `title`、`desc`、`cover`、`video_link`；
- 开关：`is_jssg_visible`、`is_news_visible`。

**谁定的：没有直接记录，从线索推断是“后台（运营）先定、开发照接”（即方式 B），待开发侧确认（R8、R9）：**
1. 开发侧 README 2026-10-30 一节已经按这些字段名写好读取逻辑，同时写着“正式 JSON 尚未创建”。也就是说，开发写代码时字段名已经定了，但数据文件还不存在。字段名是先给到开发的。
2. 字段名风格不统一，不像同一个人或 AI 一次性起的：`roundOf16` 是驼峰写法，`quarter_final` 是下划线写法；`is_jssg_visible` 里的 `jssg` 是“决赛赛果”的拼音缩写。
3. 2026-11-04 README 写着“数据结构更新”：新闻改成按语言分开存。说明字段在开发过程中由双方协商调整过。
4. 图片字段带 `storage: oss`、`originalFormat` 等上传信息，是后台表单上传图片后自动生成的格式，不是开发定的。
5. 2025 年的赛事页（`yise.xd.cn/esports/ews2025`）用的是另一个建站平台 `poster.xdcdn.net`，页面里搜不到这些字段。所以这套字段是 2026 年新建的，不是沿用旧页面。

### 用户确认理解：加了接口标记 = 后台能改（2026-11-12）

对。三层标记都意味着“后台能改”，区别在于能改什么、标在哪：

| 层 | 标在哪 | 后台能改什么 | 例子 |
|---|---|---|---|
| 开关 | **模块**（整屏或整块） | 这块显示还是隐藏 | “决赛赛果”整屏 |
| 列表 | **装重复项的模块** | 有几条，可以增删 | 晋级名单，后台加一个人就多一张卡 |
| 字段 | **单个元素**（一段文字、一张图、一个链接） | 这个元素的具体内容 | 选手名字、头像、赛程日期、奖金金额 |

没有任何标记的元素，内容写死在页面里，后台改不了。

### 增减卡片的代码在哪（用户追问，2026-11-12 查证）

**在页面里，后台只存数据。**
- 页面 `cn.html:1135` 放了一张空的样板卡 `<template id="player-card-template">`：有底图、头像位、名字位、赛区位，文字是空的。
- 页面脚本 `main.js:1345` 的 `renderPlayerList` 负责：取到后台的列表 → 每 4 人一页 → 每人复制一张样板卡（`cloneNode`）→ 把 `user_name`、`region`、头像地址填进去 → 放进轮播。
- 后台只是一张表：每行一个人。加一行或删一行，页面下次打开时就多一张或少一张卡。后台不包含任何页面代码。

对本规范的含义：
- 每个“列表”标记，都要由 Gameweb 生成一段对应的页面代码，包括样板卡、复制逻辑和分页；
- 这类代码套路固定（取列表 → 复制样板 → 填字段），适合做成通用模板，按标记自动生成，不靠手写。

### 机器怎么知道一个标记是开关、列表还是字段（✅ 机制已定 2026-11-12）

**不靠 AI 判断，靠两样东西：**

1. **标记本身写明种类（主依据）**。三种标记写法不同，设计师标的时候就选定是哪一种，例如（写法示意，最终见 F6）：
   - 「开关：is_news_visible」
   - 「列表：player_list」
   - 「字段：user_name」

   机器读到哪种就按哪种处理：开关决定显示或隐藏，列表决定复制几张，字段决定替换内容。
2. **后台数据的类型（核对用）**。三种标记对应的数据类型天然不同：

| 标记 | 后台里的数据必须是 | 实例 |
|---|---|---|
| 开关 | 是或否（true / false） | `is_news_visible: false` |
| 列表 | 一串条目（数组） | `player_list: [16 条]` |
| 字段 | 一段文字、一个数字或一张图 | `user_name: "二月晴朗"`、`score: 4`、`user_portrait: {图片}` |

种类和数据类型对不上时，机器停下上报，不猜。例如把 `player_list` 标成字段，或者把 `user_name` 标成列表。

（补充：如果字段名以后台为准，即方式 B，机器甚至可以只看数据类型推出种类；但为了规则明确，仍然要求设计稿上写明种类。）

### 模块加了开关，导航要不要也加（✅ 已定 2026-11-12：沿用 `@sec=N`，屏写 `sec/N-说明`，开关只标在屏上）

**不用在导航上再加。导航按钮只要写明“去哪一屏”，就自动跟着那一屏一起显示或隐藏。**

- 开发侧做法（`main.js` 的 `renderModuleVisibility`）：屏幕带开关 `data-visibility`；导航按钮带 `data-goto="3"`，表示去第 3 屏。某屏被关掉时，程序把所有指向这一屏的按钮一起隐藏，导航高亮的位置和“下一屏”的顺序也跳过这一屏。导航按钮本身没有开关。
- 对应到设计稿：现行命名规范已有 `@sec=N`（点了去第 N 屏），写在 `btn/` 上。导航按钮写 `btn/决赛赛果@sec=4`，第 4 屏标「开关：is_jssg_visible」，机器就知道这两个是一起的。

已定约束：
| # | 规则 | 检查方式 |
|---|---|---|
| a | 开关只标在模块（屏）上，导航不重复标 | 机器 |
| b | 导航按钮必须用 `@sec=N` 写明指向哪一屏 | 机器：导航里的 `btn/` 缺 `@sec` 就报错 |
| c | 一屏被关掉时，所有 `@sec` 指向它的按钮一起隐藏；导航高亮和“下一屏”顺序跳过它 | 机器 |

**现稿实测**：这份设计稿里**没有任何图层带 `@` 参数**。线上 Gameweb 页的导航对应关系（`官网主页 → sec1` …… `赛事视频 → sec6`）是靠按钮文字和屏名配对出来的，不是来自 `@sec`。按本规则，以后的设计稿导航按钮必须写 `@sec=N`。

#### 用户追问：导航是 `@sec=N` 还是 `@go=sec/N`（2026-11-12 核对现行规范 v2.20）

现行规范里两者分工明确：
- `@sec=<N>`：只能写在 `btn/` 上，意思是“点了去第 N 屏”。规范示例 `btn/玩法@sec=2`、`fix/侧边导航@from=2 › btn/玩法@sec=2`（naming-spec.md:116，naming-guide.md:251、270–273）。出清单时有硬性检查：`@sec` 指向的屏不存在就停（naming-spec.md:439）。
- `@go=<state>`：意思是“切到某个状态”，主要用于开弹窗，写法是抄弹窗图层名，例如 `@go=modal/顶部导航`（naming-spec.md:114）。
- `@go=sec/N` 这种写法**规范里没有**。

结论：2026-11-12 已确认沿用 `btn/导航名@sec=N`，屏写 `sec/N-说明`；不改成 `@go=sec/N`。

#### 用户追问：用 `@sec=N` 时，屏要怎么命名（核对现行规范）

- 现行规范：`sec/` 的名称**必须以编号开头**（naming-spec.md:55），例如 `sec/1-首屏`（naming-guide.md:43）。编号决定屏的顺序，也是导航的依据。
- 合法写法：`sec/4`、`sec/4-决赛赛果`（推荐，编号加中文说明）。
- 不合法：`sec/决赛赛果`。没有编号，`@sec=4` 找不到它，出清单时会被硬检查拦下。
- `@sec=4` 对应的就是编号为 4 的那一屏。编号重复会报错（`N-SEC-DUP-NUMBER`），缺号会提醒。

#### 按钮隐藏后导航怎么收缩（✅ 已定 2026-11-12）

- 是：`@sec=4` 指向的屏被后台关掉，这个按钮自动隐藏。
- 收缩按导航组在设计稿里的**自动布局**来：剩下的按钮保持原间距，按自动布局的对齐方式（居中或靠左）收拢，不留空位。
- 机器自动认出导航组“会增减”：组里有按钮的 `@sec` 指向带开关的屏，就算命中 G4 的来源 ①（接口开关）。这时导航组必须用自动布局，没用就停下上报。
- 导航选中高亮的位置、“下一屏”的顺序，都按剩下的屏重新计算。开发侧现状：导航用 flex 排列，按钮间距 `--nav-gap`，宽度 `max-content`，高亮位置按可见屏的序号计算。

### 字段名以谁为准（✅ 暂定 2026-11-12）

- **暂定 A：设计稿先定**。需求方决定改哪些，设计师在稿上起字段名，出清单时汇总字段表，后台照表建输入项。
- **待问开发（R11）**：他们是否已有成文的字段命名规范。
  - 有：以开发侧规范为准，设计稿照着起名，本条改写；
  - 没有：以后后台字段一律以设计稿为准。
