#### 2.1 可直接部署的含义

目录中每种实际需要的语言有独立 HTML；css/ 放样式与 font/ 字体，js/ 放页面脚本及集中配置，assets/ 平铺图片、视频等素材并包含 manifest.json，另有 README.md。集中配置文件名留流程确定，不在此另定新文件名。

- 从普通静态服务器打开本次交付的语言入口，无额外编译、构建或模型下载步骤，控制台不能报错；部署包不携带用于整页重建的 model.json／model.json.gz 运行模型，不影响约定业务数据 JSON（原 1.2～1.3）。
- 主体 DOM、标题、正文已在 HTML 内；可变列表可用 template 生成重复项，JS 可更新数据、状态和组件衔接，但不能重建整页主体。
- HTML 初始保留 no-js 标记，脚本启动后移除。禁用 JS 时静态内容和图片仍可见、空懒加载占位隐藏；不要求禁用 JS 后仍能切屏或读后台数据。
- QA 是独立外壳：页面不依赖壳，壳不改变产品页的成品要求。评论、清单、handoff 包、检查截图及差异图不混入部署目录；素材 manifest 应随包保留。
- 正式网址／数据地址／组件尚未接入时，按本规范的缺省状态正常显示；“可以部署”不代表正式服务已接通或上线验收完成。

#### 3.1 结构、排布与层级细则

1. 屏、固定块和内容模块均有明确身份；内容模块可多层嵌套。共用固定块只保留一份，位置及显示在哪些屏按实际设计／明确配置，不强制顶部导航、底栏和前景层全部存在。
2. 每屏按满铺背景与居中内容舞台组织。PC／手机各取对应稿数据；当前 PC 基准舞台为 19.2×10.8rem。背景可按 cover 裁切，不能把背景铺满与内容舞台缩放混为一套规则。
3. 可增减的列表、导航、TAB、社媒和开关模块，按已明确排列方向、间距、对齐、内边距、换行关系排布；增减后收拢，不留空卡或无依据的空位。上游自动布局信息如何抽取见流程待办。
4. 设计中已有图层按原遮挡顺序，包括固定块、前景、模块和内容；不能统一把所有前景放在正文之上。弹窗、展开菜单、语言层、提示条等弹出内容位于最上层；同一时间只开一个弹层。
5. 图层 z-index 采用变量或按明确顺序生成，正文不散落无依据的层级数字。未画出的固定模板内容按已定模板处理，不借此新增设计模块。

- 除 bg/、kv/ 固定素材外，设计中的 live 文字节点做网页文字，即使在 img/ 组里也不烘焙进位图；已转曲或原图自带的艺术图形按素材处理。CSS 无法保留的复杂文字效果由设计先转曲，不能由生成器自行截图替代。
- 2026-11-19 用户明确修订：bg/ 背景及 kv/ 各层作为固定素材整体导出，内部可编辑文字也随素材导出，不隐藏、抽离或另做网页文字，也不要求先转曲；该例外不扩大到 img/。kv/ 保留独立素材分层，视差按明确规则接入，不因前缀自动启用；背景 cover、各端素材和内容舞台分离要求不变。
- 每页首屏一个 h1；有普通分区标题时用 h2，每屏最多一个分区 h2。标题组可包括水印／装饰，但不凭空补装饰。
- 文字下方非文字内容构成底图；上方与文字重叠的内容分成盖层，保持遮挡；上方但不重叠的内容可并入底图。文字遮罩或特殊混合无法分层保持画面时，先报告并由设计处理。
- 底图和盖层均以所属模块左上角为定位参照，位置、宽高来自清单并换算为 rem；图层框和实际导出框分别记，阴影／外发光造成的外扩按真实偏移保留。
- 模块宽高按稿锁定；超长文字在模块内按既定换行／截断处理，不能撑走图层或靠外语内边距补偿来硬凑盖层位置。两端分别使用各自数据。
- 素材复用以同母版、同变体且未改外观的实例为依据；换图、换色或改尺寸的实例单独处理。相同导出素材可去重，这不授权删除随包保留的历史／备用文件。

#### 4.1 代码组织细则

- class 为有含义的小写英文、数字和短横线；模块英文短词最多两个词，不重复类型词。网页模块名按已明确的“英文短词-类型”对应；同名模块外壳相同，内部差异由子模块或变体区分，不同结构不能静默同名。推荐词表不强制；具体设计稿新前缀见流程 F1。
- 样式用 class，业务元素查找用 data-*，状态用 is-*；不是声称开发原样本已经完全不依赖 class。按钮用途说明复用同一份已明确动作／目标，不能另让 AI 猜一个 aria-label。
- styles.css 依次按全局、骨架、各屏、模块分段并注释；颜色、字体、时长在开头定义变量。外语／手机的共用参数通过变量覆盖，实际布局差异仍放对应样式文件。
- 禁止静态逐节点行内样式。页面自己的静态尺寸和样式写到文件中；这一约束不把已有交互中的运行时状态变化误称为静态排版。
- !important 仅保留强制隐藏／不可点、无脚本兜底、关闭中的弹层以及覆盖公司组件样式等既定用途；普通样式冲突用选择器解决。
- 页面逻辑 main.js 使用立即执行函数及严格模式；无页面框架／第三方库和构建依赖。公共组件接入后单独文件、保持原样，衔接写在页面代码中，正式接入由开发负责。
- 可使用样本已有的可选链、inert、dvh、:is()、matchMedia、ResizeObserver、visualViewport、async/await、fetch。最低浏览器版本、额外内置浏览器适配不在本版另定。
- 开发需填写的数据地址、语言网址、社媒链接与地区组合、页脚／埋点等既定参数集中到一个配置文件；不因集中配置把 SEO、正式分享内容等重新纳入 Gameweb 输入。

#### 6.1 语言与字体细则

#### 6.2 位图、SVG 和 manifest 的成品要求

- 位图每次从无损 PNG 源直接编码；不能串联 JPG、旧 WebP 或重复有损压缩。实际 alpha 任一像素小于 255 才算透明，不仅判断是否存在 alpha 通道。
- 无损 WebP 的 alpha 逐像素差为 0、可见像素 RGB 一致；完全透明像素的隐藏 RGB 不作为误报。透明边缘在黑、白及实际底色下正确。
- 有损 WebP 保持尺寸和透明要求，细线、Logo、渐变、颜色无可见劣化。quality=90 不是“保留 90% 画质”；编码器与版本需要可追溯。SSIM／PSNR 等工具、阈值和取样在流程讨论。
- SVG 必须能可靠保持整个切图边界的画面，没有嵌入位图、外部依赖或失效效果，导出框正确。包含位图或未验证效果时采用位图；无法读取完整结构或无法建立可靠基准时不能假装验证通过。具体分类／导出机制在流程中落实。
- manifest 至少保留文件来源节点／实例、格式、尺寸、字节与校验值，并增加 module、layer、box，记录所属模块、底图／盖层及相对坐标与导出框。
- 格式转换追溯字段：classification（raster／vector）、sourceFile、sourceSha256、deliveryFile、deliveryFormat（webp／svg）、deliverySha256、width、height；位图另记实际 alpha 判定、encoder、quality、lossless、method。不能用 manifest 替代缺失的资源文件。
- 原始／历史／备用素材可以随包保留，未引用不构成失败或自动删除理由；当前运行引用必须全部存在且可解码。转换后仍须用最终素材验页面。

#### 7.1 数据读取、缺省与显隐

1. 需要数据的页面从一个已配置 JSON 地址读取。初始化时请求一次，带时间戳参数、credentials: omit、cache: no-cache；地址为空不请求，不给页面新增轮询、超时或自动重试。
2. 根元素记录 loading → ready／unpublished（404）／unavailable（其他请求或解析错误）。未填或读不到时保留静态默认内容；示例姓名、比分等不能当真实数据，使用已定义“待公布”。
3. 默认内容和后台内容是两份来源；请求返回后在浏览器里覆盖显示，不把后台更新误写成 HTML 文件本身已经更新。默认值过期风险保留在流程 C2。
4. 接口内容明确区分整屏／模块开关、列表、字段及控制显示／切换的状态值。列表按条数生成；固定槽位按既定结构填值，不能把所有数据组一概做成增减列表。
5. 数据开关隐藏屏时，指向该屏的导航一起隐藏；剩余导航按明确布局收拢，翻屏与选中位置按可见屏重新计算。
6. 普通文字／数字／图片值直接共用；按语言分组的值读取当前语言项，缺当前语言的条目不显示。已有键对应：zh-CN→zh_CN、zh-TW→zh_TW、en→en_US、ja→ja_JP、ko→ko_KR；不代表每页必须具备这五种语言，新增语言需明确映射。
7. 可变范围可按项目扩展至日期、奖金、标题等运营常改内容；是否可变由明确业务范围决定，不让 AI 看外观猜。后台建字段和正式发布由开发负责，其支持能力仍待具体项目核实。
8. 外部文字通过 textContent 写入；外链仅 http(s)。数据读取／展示是 Gameweb 的交付能力，正式接口接通归开发，内容真实性归需求方。

#### 8.2 导航、TAB、轮播、弹层细则

- 导航选中背景位于对应按钮中心，320ms 滑动、略冲过再回退；既定冲过量约为 0.12×--nav-unit。TAB 的冲过量为 0.12rem。同组选中图必须相同才共用滑动；不同则各自换图，不强行滑动。首次加载不播滑块、连续操作从当前可见位置接续。
- TAB 使用 button 的 role=tab、aria-selected、aria-controls 对应 role=tabpanel；未选面板 hidden。重复点当前项不重播；只有一个阶段时按实际按钮宽度居中。
- 卡片轮播按实际条数／设计每页数量向上取整；不同内容轮播按设计的独立页面模块数。圆点数跟实际页数，不按稿上复制的圆点数量硬写。
- 多页轮播可向前／向后无限循环，越过末页时沿同方向无缝衔接；横滑同样循环，非当前页 inert。末页不足不补卡，整体居中。
- 0 条时只显示已定义空状态，卡片、箭头、圆点和页码均隐藏。1 页时显示卡片，隐藏箭头／圆点，只有稿上存在页码才显示 01/01。多页正常显示，页码“当前／总数”两位补零；没画页码不生成。
- 菜单与语言层 200ms 渐入渐出；打开移入焦点，关闭还给触发按钮；关闭按钮、Esc 和语言层已规定的外侧点击可关闭；互斥、关闭中不可点，快速反向操作从当前状态接续。不能给所有弹窗擅加同一关闭策略。
- 社媒采用新窗口 http(s) 链接、rel=noopener noreferrer、可识别的用途说明和内联 SVG 图标；微信二维码支持悬停／键盘聚焦，手机隐藏微信。具体地区组合与链接由开发配置，不把样本按钮数量定死。
- 后台外链卡片支持点击／键盘激活；无链接或格式不对，按当前语言提示“待公布”，封面失败使用已有默认封面。外链视频播放由目标网站处理，不新增本地播放器。
- 全页共用 id=site-status、role=status、aria-live=polite 的提示条，层级按弹出内容处理。按钮和链接保留 focus-visible 边框；沿用轮廓 0.03rem、偏移 0.05rem 的方式与页面色彩变量，不增加设计标记。

**2026-11-20 生效修订：动画实现代码必须符合开发侧页面代码规范，是送验硬条件；具体效果及其时长、延迟、方向、距离、曲线、播放节奏等参数标注为“后续可调”。** 本文第8～9节及所引用动效表中的效果数值保留为既有方案与来源，不再作为不可调整的送验门槛；后续效果按当次明确要求修改，不授权AI自行改设计。输入手势阈值、目标关系、内容状态和其他非效果要求不因这条修订自动变更。

#### 9.1 动效对象与播放约束

六类为：普通分区标题、内容模块、交互组件、前景装饰、首屏组合开场、页面切换。同类对象在同种触发下采用同一套已定规则；固定组与重复组可共用基础效果，但整组、逐项、分批的作用单元必须明确。

- 普通分区标题包括标题与组内水印／装饰一起运动；首屏 slogan、卡片小标题不自动套用该规则。
- 正文、姓名、排行行等随所属模块整体运动，不再逐字／逐段叠加；不把所有 img/ 当成前景或自动添加漂浮。
- 只在实际进入新屏、TAB／轮播变化等既定条件触发；隐藏 TAB、轮播页及另一设备副本不参与当前入场。切换或展开页脚时收束相关旧入场。
- 逐项／分批开始间隔为 60ms：四项为 0、60、120、180ms；同批内部同时开始。整组同时展开不额外加逐项间隔。首屏 80／180ms 延迟、前景 120ms 间隔保持各自含义。
- 减少动画时取消主要入场、闪烁、切屏、滑块、轮播过渡、底栏和箭头跳动，背景视频不播放；交互仍可用。菜单不支持 element.animate 时直接显隐。
- 动效最终位置仍来自清单；手机／PC 使用明确各端的方向距离。未列方向、曲线、距离、数量／排布不得自行推算；新情况先明确后处理。

| 实际卡数 | PC 从左到右 | 手机双列按页面顺序 |
|---|---|---|
| 1 | 0 | 0 |
| 2 | +0.35rem、-0.35rem | +0.14rem、-0.14rem |
| 3 | +0.60rem、0、-0.60rem | +0.14rem、-0.14rem、0（末行居中） |

#### 9.3 首次与返回首屏的时序

首次等待当前端背景、slogan 加载／解码成功或失败，到可绘制帧后从 0 计时：0ms 背景开始；320ms 顶栏与手机底栏开始；440ms 顶栏晶体开始；480ms 社媒开始；600ms slogan 滑入开始；700ms 内部闪烁开始；约 1300ms 首次开场阶段结束，满足条件才尝试背景视频。

返回首屏时背景仍渐显，slogan 滑入延迟 80ms、闪烁延迟 180ms；不重播顶栏／社媒的首次入场。1300ms 是动画计时，不是资源等待超时。只对实际设计中存在的对象应用，样本手机首页底栏等不能覆盖“按实际稿显示”的规则。

#### 10.1 加载、失败与保护细则

- 首次只预加载当前语言、当前端的首屏静态背景，不同时预加载 PC 和手机背景；非首屏图片按需请求。slogan、导航、当前可见内容及必需 CSS／JS／字体照常加载。
- 背景视频不参加首屏预加载；手机／减少动画初次打开不请求视频，组件不存在跳过。组件接入后，真正播放才盖住静态内容。
- 动态头像或封面地址缺省／失败，回到已有对应默认图；默认图也失败不循环换图或不断请求。视频加载／自动播放失败恢复静态背景和 slogan，其他内容正常，不新增错误弹窗。
- 普通背景图、Logo、装饰图和默认图失败后的统一显示方式未加入本规范，由开发按具体项目处理；不能把这个职责排除解释为允许缺素材交付。
- 页面资源没有额外等待截止时间、超时主动中止、自动重试或定时轮询。挂起时维持既有等待行为；不改变浏览器／网络自身超时，也不禁止用户刷新。工具执行超时、动画计时和提示条消失计时不在这条限制内。
- 不另定首屏秒数、Lighthouse、LCP／CLS／INP 等数值门槛。慢网测试中的延迟不是页面超时标准；体积建议和已定加载行为仍需满足。
- 正文选择、复制／剪切、原生拖出、右键限制同时覆盖产品页与 QA；输入框、textarea、可编辑区域和明确复制按钮可正常使用。保护不能误伤按钮、滑动、键盘和编辑，也不承诺防截图或彻底防下载。

#### 2.1 Onepage 制作 Skill——弄清开发做这种页面的原始规则

**请开发给什么**

制作 ews2026 时实际使用的 **site-components/skills/onepage-template/ 完整目录**：SKILL.md、它实际引用的模板／脚本／参考文件（如有），以及使用的版本或提交号。给目录包，或可读取的仓库位置和版本都可以；只给 SKILL.md 的截图不够，里面引用的文件也需要能读到。

**我们为什么要**

开发的 README 明确写了 Onepage 行为参考这份 Skill。现有 HTML 只能告诉我们“这一页最后做成了什么”，Skill 才能说明开发原本怎样组织整屏切换页、哪些规则是固定的、哪些可以随项目变化，避免继续只靠一个成品反推。

**拿到后怎么用**

先读 Skill 和配套文件，对照已经定好的 HTML v1，找出可复用的模板与行为规则、已有样本没有说明的约束。再把结论用于后续“ready 清单怎样生成静态 DOM、交互和适配代码”的流程讨论。设计内容和几何仍来自清单，不改成让 AI 看图猜；Skill 也不会自动覆盖已经确认的 v1 调整。

**现在已有／还缺**

已知准确的引用路径，但完整 Skill 尚未取得。拿到资料不代表已经安装、执行或决定直接使用它。

**怎样判断这份资料交得合格**

- 交的是可读取的 Skill 文件和真实目录，不只是名称、截图或开发电脑上的绝对路径。
- SKILL.md 引用的必要模板／脚本／参考文件能找到；外部依赖有明确位置和取得方式。确实没有配套文件时，说明没有即可，不要求额外创造。
- 能确定是哪一个版本、是否为制作 ews2026 当时使用的版本；如果给的是更新版，说明与样本所用版本的区别。
- 接收后能读懂它的输入、产出和使用前提。缺文件或引用失效时列明待补，不因收到一个 SKILL.md 就算完整。

这里核对的是资料完整和可读，不在接收时自动安装依赖、执行脚本或改动现有项目。

#### 2.2 制作页面直接用的模板、动效和资源——让 Gameweb 有可用的制作材料

**请开发给什么**

只给这次页面制作实际要复用的文件及必要说明。例如：

- 页面里的闪烁动效样式及其用法，来源线索为 website-components/components/flicker-entrance/。
- Onepage Skill 或制作模板引用、但现有工程没有的配套文件；已在上一项提供的不再重复要。
- 如果继续使用开发样本里的字体，补缺失的字体来源／许可说明。
- 确认我们持有的 ews2026 工程对应哪个可参考版本；若缺必要文件，只补那些缺件。

**我们为什么要**

这些会影响 Gameweb 最终生成的页面：例如缺闪烁样式就无法按已定方式做开场效果，缺指定字体就无法按稿显示文字。我们要的是制作所需的文件和用法，不是整个公司的组件库。

**拿到后怎么用**

在流程讨论中确认哪些文件可以直接复用、哪些要随页面输出，并核对它们与已定动效／字体规则是否一致。后续获准制作时，再把实际使用的样式和字体纳入页面目录，保留来源记录，用最终文件检查画面效果。原始素材的尺寸和位置仍按设计清单，不靠这些参考文件补画设计。

**现在已有／还缺**

本地已有 flicker-entrance.css、页面样式、素材及字体目录。样本闪烁只复用了 CSS，没有加载该组件 JS；不用为此索要或接入整套组件。需要的是所用版本／用法、实际依赖缺件，以及选用字体缺失的来源说明。

正式页脚、背景视频播放器、埋点 SDK 及其源库不属于这项当前素材请求；这些由开发接手后接入，Gameweb 只按已定标准预留入口。

**怎样判断这些素材交得合格**

- 交付的是制作实际需要的原文件，不是效果截图；文件可以打开或解析，内部资源引用没有缺件。现有工程中已具备的，可直接指出对应文件与版本。
- 动效样式附最简用法：应用在哪个元素、依赖哪些文件或状态、如何触发。已有说明可以直接提供，不要求重写组件文档。
- 实际使用的字体有可读取文件，以及来源／许可说明；缺失只补相关字体，不要求提供所有公司字体。
- 标明文件是否改过、适用哪个样本／版本；没有实际使用的组件文件不为了“完整”强行加入。

接收方据此登记“可用于哪一块页面、还缺什么”。能读文件不代表效果已经通过浏览器验证，后续制作仍需按 v1 检查。

#### 2.3 页面字段说明和 JSON 样例——让 Gameweb 知道数据怎样变成页面内容

**请开发给什么**

- 字段对应页面的哪类内容，列表如何嵌套，语言如何区分。
- 没有值、没有列表内容或开关关闭时是什么意思；如有限制，说明允许的数量和类型。
- 有现成字段命名规范一并提供；如果后台能力会限制页面准备哪些字段，只说明这项具体限制。

样例用虚构或脱敏内容即可，不需要正式名单、比分、真实接口地址或后台账号。页面自身是否需要动态数据，仍按实际项目范围确定。

**我们为什么要**

设计稿只画出某一刻的样子，不能告诉 Gameweb 哪些内容以后会变、哪些是重复列表、哪些控制整块显示。没有这些说明，生成器就不知道该把数据填到哪里，也不知道条数变化后该怎样分页和显示空状态。

**拿到后怎么用**

用字段说明核对设计阶段明确的内容与数据关系，讨论清单需要怎样记录；后续再据此生成 HTML 中的重复项模板，以及读取 JSON、填文字／图片、处理列表／开关和语言的页面代码。用示例数据检查空列表、单页、多页、字段缺省等已定情况，避免测试时依赖真实后台。

比如“选手列表”是一组重复数据，Gameweb 就需要生成对应卡片并按已定轮播规则分页；控制某屏的开关关闭时，该屏及对应导航一起隐藏。这个说明决定的是页面代码行为，不是怎样管理后台。

**现在已有／还缺**

已有样本字段观察和页面读取代码；开发确认的字段约定、样例及命名说明仍待补。新页面若没有开发既定字段，按已确认的“设计稿先定”方向准备字段，再核对实际限制，不能把“还没给”当作“后台一定支持”。

后台入口、权限申请、操作手册、发布流程不在本次资料范围内。正式数据和接口接通留开发后续处理。

**怎样判断数据资料交得合格**

- JSON 是可解析的文件，示例值与字段说明的名称、类型和嵌套层级一致，不只给一张后台截图。
- 说明能区分固定值、重复列表、显隐开关和语言内容，并能知道它们对应页面哪类内容。
- 对实际存在的空值、空列表、缺字段、无当前语言内容等情况，说明其含义和已有约定；有条数或类型限制则写明。未定的部分明确标出来，不伪装成已经支持。
- 样例只需足以说明结构，后续空列表、单页、多页等测试数据可由 Gameweb 按约定构造，不要求开发准备整套测试报告。
- 有现成字段命名规则就一起给；没有则明确没有，按已经确认的设计字段方向继续对齐。样例不依赖真实接口可访问，也不夹带生产账号或密钥。

接收方先比对“说明与样例是否一致、是否足以写出页面读取逻辑”；不把后台已经建好或正式数据已经发布当作资料通过条件。

#### 2.4 已有制作和验收方法／要求——让 Gameweb 按同样的尺度取数和检查

**请开发给什么**

现有的简短说明、脚本或文档即可：

- 用什么工具读取 Figma 节点数值、怎样导图，尤其是导出范围、倍率和文字处理。

**我们为什么要**

同一张设计稿，如果取数、切图边界或验收尺度不同，最后页面可能不一致。这些资料用来理解开发实际采用的方法，避免 Gameweb 漏掉已存在的要求或重复造一套工具。

**拿到后怎么用**

对照 Gameweb 现有的清单抽取、素材导出、编码与页面检查能力，找出可复用的步骤和缺口，记入后续流程待讨论事项。比如导出倍率影响源图检查，验收用例影响测试数据准备。具体怎么选工具、怎样校准阈值仍在流程阶段决定；开发没有正式标准时，不凭空新增数字。

**现在已有／还缺**

已有开发提交版 README 中的部分制作与验收记录，但没有完整说明具体取数工具等细节；也没有取得统一的正式图片／视频／性能标准。现在的 WebP 参数已按 v1 确定，15 MB 单视频／120 MB 整包仍是暂定建议。新资料如与已定要求冲突，列清差异再讨论修订，不自动替换。

**怎样判断方法和要求说明够用**

- 取数／导图说明能定位使用的工具及其版本或环境，并说明节点、范围、倍率和文字处理这些影响结果的步骤；现成文档、脚本或简短操作说明均可。
- 验收依据写清检查对象与条件，例如参考设计、端别、语言、视口、静态状态，以及哪些做过、哪些未验证；不能只给一句“验过了”。已有记录已说明的内容无需重复写。
- 有数值要求时说明单位、适用范围和测量条件，并区分“正式要求”“样本做法”“暂定建议”；没有正式标准就注明暂无，不要求开发临时编造。
- 接收后能判断该资料用于哪个 Gameweb 制作／检查环节；仍不能确定的地方列出具体问题，后续再讨论，不自动提高或降低 v1 要求。

下表沿用本分组已整理的 A01～A12。表内“原规范第 X 节”对应第一篇的小节编号；它是已有要求的检查编排，不能覆盖第一篇完整细则，也不能把第二篇待定方法视为已实现。

### 验收项目、通过条件与证据

验收以**本次实际交付版本**为对象，覆盖实际语言、端别及已有功能。以下按结果组织检查，不预先指定新状态机、工具、命名语法或界面。程序可验证的先用程序检查；已定人工核对保留，其中交互必须先程序白盒通过，再人工黑盒通过。

|---|---|---|---|
| A01 产品包与运行入口 | H01～H05 | 实际语言入口与必要目录齐全；无构建、无 QA 依赖、无整页模型重建；禁用 JS 仍有静态内容和图片；本地引用齐全、控制台无错 | 目录／源码检查；普通静态服务逐入口打开及 no-js 结果；检查记录对应实际产品包 |

### 判定规则

1. 各项独立判断：内容完整、画质、整页视觉、交互和交付边界不能相互抵消。像素结果正常不能豁免缺字、错图、字体错误或错误目标。
2. 交互白盒与人工黑盒必须均通过；任何一道失败或未验证，都不能标记交互通过。自动操作可以辅助检查，但不能替代已定的人工黑盒。
3. 未执行、缺基准、读取失败、跳过或旧版本证据不能当作通过。现有包级测试、旧项目检查全绿也不能代表当前页面符合新标准。
4. 没有对应功能或端别时可说明不适用；缺实现、缺数据、缺设计或暂时测不了，不属于“不适用”。明确缩小交付范围须先取得用户决定。
5. 本次范围内所有适用要求通过，且最终包与验收结果一致，才可声明本次设计交付完成。开发负责的正式服务与上线状态另行验收。

验收结论可用以下状态明确表达，具体报告文件格式留流程确定：

| 状态 | 含义 |
|---|---|
| pass | 已对当前产物执行检查，有可追溯证据且符合要求 |
| fail | 已检查并发现不符合项，必须指出位置与失败原因 |
| not_run | 尚未执行、缺输入／基准／方法或执行中断；保留阻塞原因，不计通过 |
| n_a | 已确认的实际范围不包含此功能或端别，说明依据；不拿它掩盖缺项 |

### 验收证据应能回答的问题

- 验的是哪一版最终文件，对应哪份设计／清单、字体、文案和素材？
- 验了哪些语言、端别、视口、模块、交互及数据状态？
- 每项要求由程序或人工怎样核对，实际结果是什么，证据在哪里？
- 哪些失败、未执行或不适用，原因是什么？当前是否仍有阻止交付的事项？
- 验收后的打包、重新抽取、改文案、换素材或改代码是否影响已有结果？受影响的旧证据不得直接当成新版通过，具体重验范围和记录方式在流程阶段落实。

证据必须来自实际产物。本文只定义证据需要证明的事实，不预定报告 schema、哈希算法、截图工具或人工核对界面。
