# 第 4 项：命名与 class 体系

状态：✅ 已定（2026-11-12）

> v1 成品要求已定稿；当前 class 要求以“4.1 已定”和 4.2 为准，早期方案仅保留讨论来源。命名扩展、检查器和交互信息补齐仍归 Gameweb 流程 F1／F8／F9；示例不等于现行命名规范已支持，也不代表交互已经能完整自动接线（见 17.7b）。

## 分工说明

- **层级**：已定，跟着设计稿的命名层级走（3.3a）。
- **设计师在 Figma 里怎么写模块名**：留到改命名规范时定（F1）。
- **本项已定**：网页 class 的写法风格及与模块身份的对应原则；具体命名扩展与生成工具归流程。

## 现状

**开发侧**：class 一律用英文、小写、短横线连接，表达语义。例如 `schedule-page`、`rank-card`、`rank-row`、`player-card`、`prize-panel`。这些名字是 AI 自己起的。

**设计稿现有图层名（本稿 PC 端，338 个组或框没有前缀）**：
- Figma 默认名 185 个，例如 `Frame 1312316931`；
- 其他英文 78 个；
- 中文 69 个，例如 `小组卡片`、`角色信息框`、`区域预选赛奖金`、`标题模块`、`社媒`；
- 纯数字 6 个，例如 `1`、`2`、`3`。

**Gameweb 清单**：只有角色前缀（`img/`、`btn/` 等），没有模块名。

结论：现在**既不能直接用设计稿图层名，也不能直接用清单**。大半是默认名，中文名也不统一（同一类东西有的叫“卡片”、有的叫“框”），而且是中文，变不成开发侧那样的英文 class。

## 4.1 设计稿上的模块名怎么变成网页 class（✅ 已定 2026-11-12，最终方案见“4.1 已定”；下面 A/B/C 是早期方案，B 已放弃）

可选方案：
- **A. 设计师直接写英文**：稿上写 `rank-card`，网页原样使用。最直接，但设计师要会起英文名，而且每份稿各起各的，不统一。
- **B. 固定词表（推荐）**：命名规范里维护一张“中文模块名 → 英文 class”的词表，例如 `排行卡 → rank-card`、`选手卡 → player-card`、`赛程卡 → schedule-card`。设计师从词表里选中文名写进稿里，网页按词表换成英文。词表里没有的名字，机器停下上报，补进词表后再继续。跨页面名字统一，设计师也不用写英文。
- **C. AI 翻译**：违反“不靠 AI 判断”的原则，不推荐。

## 4.0 用户追问一：导出哪些东西当素材，开发侧怎么控制颗粒度（2026-11-12 查证）

**Gameweb**：`img/`、`bg/`、`kv/` 就是导出边界。标了前缀的组整体导出一张图，里面的子图层不再单独导出（清单里 494 个 `slice-child`）。颗粒度由设计师的命名决定，结果是确定的。

**开发侧**：没有成文规则，由 AI 逐个判断，再按用户的要求反复调整。从 README 和 manifest 能看出这几条做法：
1. **按“排版时需要独立挪动的最小单位”拆。** 线上签表原来是 4 张整行背景，后来拆成 5 种独立素材：标签 `match-label.svg`、对阵底板 `match-card.png`、合流线 `bracket-merge.svg`、晋级线 `bracket-advance.svg`、晋级底板 `bracket-finalist.png`。拆开后才能用 flex 正常排版。这比设计稿的 `img/` 分组拆得更细。
2. **能合的合。** 轮次标题原来 15 张碎图，合成 5 张整图（`round-heading-*.png`）。
3. **相同的图只导一次，反复用。** cn.html 里图片引用 880 处，实际只有 126 个文件；排行行底图 `rank-normal.png` 一张用了 96 次。
4. **线条和矢量导成 SVG**（16 个）；导图时去掉空白边（“去除父 frame 中的空白”）；文字一律排除。
5. **有些素材是用户另外提供的**，例如导航背景 `nav-background.jpg`、奖金装饰 `finals-prize-card.png`。

结论：开发侧的颗粒度由“排版需要”决定，但靠人和 AI 判断。按本规范的原则，改为**由设计稿命名决定**：
- 导出边界沿用 `img/`、`bg/`、`kv/`；
- 需要独立排版的部分（例如签表连接线、卡片底板），由设计师拆成单独的 `img/`；
- 再叠加已定规则：文字排除（5.1～5.5）、盖层单独导出（5.6）、重复项只导一份（G2）、像素完全相同的图只保留一份（按校验值去重）。

## 4.0 用户追问二：设计稿名和网页名保持一致，目的是什么？必须用开发侧的 rank-card 吗？

**保持一致的目的：**
1. **机器能对上号**：检查器要知道设计稿里的“排行卡”对应网页里的哪一块，才能逐块做截图比对、核对数值，以及追溯素材来源（manifest）。
2. **能重新生成**：维护方式定了 c，结构由 Gameweb 重新生成。名字稳定，重新生成时才能找到同一块，不打乱开发改过的配置和数据部分。
3. **人好定位**：设计或 QA 说“排行卡第二行”，开发能直接在代码里搜到。
4. **跨页面统一**：每个页面同一种东西叫同一个名字，样式和组件能复用，开发接手也不用重新认。

**必须用开发侧的具体单词吗？不必。** 开发侧的约定里，脚本是靠 `data-*` 属性找元素的，不靠 class 名；class 名主要用于样式和阅读。所以要求的是：
- 风格和开发侧一致：英文、小写、短横线连接、表达语义；
- 设计稿名和网页名一一对应，规则固定；
- 同一种东西在所有页面里叫同一个名字。

早期提出把开发样本名称列入固定词表；该方案已放弃。当前按 4.1b／f：英文短词自行命名，词表仅推荐，不强制。

## 4.0 用户追问三（2026-11-12）

### ① 签表连接线是什么，我需要把什么拆成单独的 img/

开发侧的线上签表由 5 种零件拼成：
- `match-label.svg`：比赛编号的六边形小标签（175×50）；
- `match-card.png`：一场比赛的双人底板，上下两格各放一个选手名（428×151）；
- `bracket-merge.svg`：把上下两场比赛连到下一轮的“]”形合流线（141×179）；
- `bracket-advance.svg`：带菱形箭头的晋级横线（195×21）；
- `bracket-finalist.png`：晋级者的单人底板（428×116）。

开发侧拆这么细，是因为它让**文字按正常排版流动**，底板和线条必须跟着文字所在的格子一起排。

**按本规范已定的规则（5.8 选 B：图层钉在模块上，不跟文字流动），这类拆分大多不再需要。** 签表的格子数量固定（16 / 8 / 4），整块底图导出一张即可，名字按坐标钉在上面。

设计师需要拆成单独 `img/` 的，只有三种情况：
1. **会增减的组里的每一项**（G4）：例如排行行、选手卡、新闻卡。每一项的底图是单独的 `img/`，才能按接口条数复制。
2. **有状态切换的东西**：例如 TAB 的选中和未选中、按钮的普通和高亮。每种状态各一张。
3. **要单独动的东西**：例如有入场动画的插画、导航的选中滑块。

其余情况整组导出即可。挡住文字的盖层，由机器按 5.6 自动拆，设计师不用管。

### ② 重复的图能不能按设计稿组件判断，追溯到组件母版

可以，而且应该作为第一判断依据：**同一个组件母版（同一个变体）的实例，只要没有改过外观（换图、换色、改尺寸），就直接复用母版导出的那一张图。**

现状提醒：这份稿 PC 端 171 张切图里，只有 7 张是组件实例（来自 2 个母版）。其余大多是复制粘贴的普通组。所以还需要第二道保险：**导出后像素完全相同（校验值一样）的图，只保留一份**。Gameweb 清单里已经有每张图的 `sha256`，可以直接用。

素材复用规则（已确认，工具改造归流程）：
- 4.0a 组件实例没改外观的，复用母版素材；
- 4.0b 改过外观的实例，单独导出；
- 4.0c 导出后按校验值去重，完全相同的只保留一份；
- 4.0d 【建议给设计侧】会重复出现的东西尽量做成组件，素材更少、更好维护。

### ③ 每个页面模块不同，难道每次都定新词记录在案？

确实不现实。修改方向：**词表只收“类型”，不收具体名字。**
- **类型词**：几十个通用词，跨页面通用，几乎不增长。例如 卡片 `card`、列表 `list`、行 `row`、切换 `tab`、面板 `panel`、轮播 `carousel`、标题 `title`、按钮 `btn`、弹窗 `modal`、导航 `nav`、横幅 `banner`。
- **具体名字**：每页自己起，不进词表。由设计师在模块名里写一个**英文短词**，例如 `player`、`rank`、`schedule`。
- 网页名由机器自动拼出：`具体名-类型`，例如 `player-card`、`rank-row`、`schedule-card`。这和开发侧的名字一模一样。
- 早期“缺英文短词时退回类型＋序号”的建议已被 4.1a 的必填要求取代，不作为现行规则。

### ③ 补充：落到设计稿上怎么命名（示意，最终写法在 F1 定）

以本稿第 3 屏的排行卡为例（实际图层树取自线上页 model）。

**现在稿上：**

**改成（示意）：**

**网页里自动得到：** `region-panel` › `rank-card` › `rank-list` › `rank-row`，和开发侧一致。

**设计师要做的事：**
1. 只给“模块”这一层改名，格式是 `类型/英文短词 中文备注`。类型从固定小表里选，英文短词自己起，中文备注随意写，方便阅读。
2. 已有前缀的图层（`sec/`、`fix/`、`img/`、`btn/`、`switch/`、`tab/` 等）照旧。
3. 纯排版用的 `Frame 1312…` 不用改。现行命名规范已有“无前缀的纯布局 frame/group 透明”的规则，机器会直接穿过去。
4. 文字图层不用改名。

**类型小表（初稿）：** 面板 `panel`、卡片 `card`、列表 `list`、行 `row`、项 `item`、轮播 `carousel`、标题 `title`、横幅 `banner`、导航 `nav`、弹窗 `modal`。已有的 `tab/`、`switch/`、`dropmenu/` 沿用现行规范。

### ③ 再补充：类型前缀和现有前缀的关系（2026-11-12）

写法相同，都是“前缀/名字”，机器靠前缀认图层。分工上略有区别：
- **现有前缀主要告诉机器“怎么处理”**：`sec/` 是一屏，`fix/` 钉在屏幕上，`img/` 导出成图，`btn/` 可点击。
- **新的类型前缀主要告诉机器“这是什么模块、叫什么名字”**：`card/`、`list/`、`row/`、`panel/`，用来搭结构、起网页名。
- 少数类型前缀也带行为约束，例如 `list/` 表示里面的项会增减，必须用自动布局（G4）。

待改命名规范时处理（并入 F1）：一个图层既是模块又能点击时怎么写。例如开发侧的视频卡 `video-card` 本身就是按钮。

### ③ 用户追问：前缀撞车怎么办；自己起的名字不统一，同是卡片但内容和可替换性不同怎么区分（2026-11-12）

**前缀撞车（一个图层既是模块又要能点）：**
- 现行规范里，`@link=`、`@go=` 这类“点了干什么”的参数只允许挂在 `btn/`、`hot/` 上。
- 方向建议：**一个图层只用一个前缀，前缀管“是什么”；“点了干什么”统一用 `@` 参数表达**。允许把 `@link=`、`@go=` 挂到类型前缀上，例如 `card/video 视频卡@link=video`，这张卡就同时是模块和可点击按钮。
- 备选：外层写 `card/video`，里面放一个铺满的透明热区 `hot/@link=video`。不改规则，但多一层。
- 具体写法并入 F1。

**名字不统一的问题：**
- 开发侧也没有跨页面统一的名字表。`rank-card`、`player-card` 是开发侧（AI）为这一页起的；开发侧统一的只是**写法风格**（英文、小写、短横线、有含义）。所以“设计师起英文短词”和开发侧的实际做法一致。
- 不同页面的“选手卡”长得不一样，样式本来就没法直接复用。能跨页复用的是行为（轮播、切换、列表增减），这由类型前缀和参数决定，不靠名字。

**“同是卡片，内容和可替换性不同”怎么区分：拆成三个互不相干的维度，名字只管其中一个：**

| 维度 | 由什么表达 | 例子 |
|---|---|---|
| 是什么类型 | 类型前缀 | `card/` |
| 是哪一种 | 英文短词（同一页内唯一） | `card/rank` 和 `card/player` 是两种卡 |
| 能不能替换、点了干什么 | 接口标记（G6 三层）、`[replaceable]`、`@` 参数 | 选手卡的名字标接口字段；视频卡挂 `@link=` |

配套硬规则（机器检查）：
- **同一页里同名必须同构**：两个都叫 `card/rank` 的组，内部结构必须一样（最好是同一个组件），否则报错。
- **结构不同就必须换名**。

可选：给赛事、活动类页面列一份“推荐短词”（例如 player、rank、schedule、prize、video、news），只做推荐，不强制。

### ③ 用户追问：一定要英文吗；外形相同、底部细节不同的卡片要不要区分命名（2026-11-12，附用户示例图：三张“赛季卡”）

**中文行不行：**
- 网页技术上允许中文 class，但开发侧的写法一律是英文，按 P8 应该和开发侧保持一致。
- 中文要变成英文，只有三条路：
  - 设计师自己写英文；
  - 查固定词表（前面讨论过，词太多，记不住）；
  - 机器翻译或转拼音。AI 翻译违反“不靠 AI 判断”；拼音（如 `sai-ji-ka`）规则固定，但不符合开发侧“名字有含义”的风格。
- 已按下方 4.1a～b 确定：英文短词必填、中文备注选填，不用 AI 翻译。

**用户示例：三张赛季卡**
- 外壳完全一样：外框、顶部菱形标、标题、主图。
- 底部各不相同：
  - 卡 1：一排奖品，可以左右滑；
  - 卡 2：一排奖品，固定不动；
  - 卡 3：礼包码加“复制”按钮。

**开发侧对这类情况的做法（cn.html:184、190）：**同一个基础名，加一个区分名。`<article class="prize-panel regional-prize">` 和 `<article class="prize-panel finals-prize">` 都是 `prize-panel`，外形样式共用；`regional-prize` 和 `finals-prize` 各管自己不同的部分。

**建议：外壳同名，差异由“子模块”或“变体名”体现**
```
card/season 赛季卡                     ← 三张卡外壳同名
├── img/卡框
├── 标题（文字，标接口字段）
├── img/主图
└── 底部，三张卡各不相同：
    卡 1：scroll/reward 奖励 @x          ← 现行规范已有 scroll/（可滑动区）
    卡 2：list/reward 奖励               ← 固定排列
    卡 3：row/code 礼包码 → 礼包码文字 + btn/copy 复制
```
- 网页里三张卡都叫 `season-card`，外框、标题、主图的样式共用一份；底部各自是 `reward-scroll`、`reward-list`、`code-row`。
- 如果设计稿把这三张做成同一组件的三个变体（例如变体属性“底部=滑动/固定/礼包码”），网页再给每张加一个区分名，例如 `season-card is-scroll`，做法和开发侧的 `prize-panel regional-prize` 一样。
- 因此“同名必须同构”修订为：**同名 = 外壳结构相同；内部的不同之处必须由子层自己的前缀或变体名表达，不能悄悄不一样。**
- 新发现的缺口：现行规范没有“复制到剪贴板”这个动作（`@copy` 之类），并入 F1 一起定。

### ③ 用户追问：英文短词已经负责对应，中文还有什么用（2026-11-12）

- 对机器来说**没有用**，机器只读前缀和英文短词。
- 中文只是**给人看的**：设计、策划、QA 在 Figma 里一眼看懂这块是什么，不用去猜英文。
- 现行规范里，`img/卡片背景`、`btn/社媒按钮`、`sec/1-首屏` 这些名字本来就用中文。那些图层不生成网页 class，中文随便写。
- 建议：模块层**英文短词必填，中文备注选填**，机器忽略中文。写不写由设计团队的习惯决定。

### ③ 用户追问：英文短词写什么，有没有规定（2026-11-12）

**由设计师自己起，不设强制词表。** 但有几条硬格式和一份推荐词表。

硬格式（机器检查，不合格就报错）：
1. 只能用小写英文字母、数字、短横线，最多 2 个词，例如 `player`、`gift-code`；
2. 不要重复类型词：写 `card/player`，不要写 `card/player-card`；
3. 同一页里同名必须同构（外壳相同，差异由子层表达）；结构不同必须换名。

起名原则（人看，不由机器判断）：
- 说**内容是什么**，不说长什么样：用 `reward`，不用 `blue`、`left`、`big`；

## 4.2 网页里的“行为标记”和“样式名”分开（✅ 已定；业务选择器要求比样本更严格）

**开发侧：**
- **样式名（class）** 只管长什么样，例如 `rank-card`；
- **行为标记（`data-*`）** 只给脚本找元素用，例如 `data-goto="2"`（导航到第 2 屏）、`data-region="cn"`（赛区按钮）、`data-carousel`（轮播）、`data-next-page`（下一屏按钮）、`data-visibility="is_news_visible"`（接口开关）；
- 2026-11-16 源码复核更正：开发脚本也使用 class 找元素，例如 main.js 的 `.region-panel`、`.rank-card`、`.name` 以及轮播结构查询。此前“从不靠样式名找元素”的描述不准确；4.2a 已定要求保留，但应列为比样本更严格的分工，不能标成完全原样；
- 状态用 `is-` 开头的样式名，例如 `is-active`（当前选中）。

**Gameweb：** 每个块都挂了一大堆来自 Figma 的标记（`data-node-id`、`data-figma-type` 等），交互挂在 `data-nav-screen` 这类标记上，样式名统一是 `ews-node`。

**已定规则：**

| # | 规则 | 原样 / 优化 | 检查方式 | 信息来源 |
|---|---|---|---|---|
| 4.2a | 样式名只管样式；脚本只认 `data-*` 行为标记，不靠样式名找元素 | 已确认加强；样本仍有 class 查询 | 机器：扫描 JS 选择器，不允许出现按 class 查找业务元素 | 已定要求；2026-11-16 更正样本归类 |
| 4.2b | 状态一律用 `is-` 开头的样式名：`is-active`、`is-silver` 等 | 原样 | 机器 | 固定模板 |
| 4.2c | 交付页面里不带 Figma 调试标记（`data-node-id`、`data-figma-type` 等）；追溯靠 `manifest.json` | 原样（开发侧没有这些） | 机器 | 固定模板 |

### `@`、`data-*`、`is-` 三者的关系（用户追问，2026-11-12）

| 东西 | 写在哪 | 谁写 | 管什么 | 什么时候起作用 |
|---|---|---|---|---|
| `@` 参数 | 设计稿图层名 | 设计师 | 这个东西**点了干什么**（`@go`、`@link`、`@sec`） | 生成网页时，被机器读走 |
| `data-*` 行为标记 | 网页代码 | 机器根据 `@` 参数和前缀自动生成 | 让程序找到“这是导航按钮、这是赛区切换” | 页面运行时 |
| `is-` 状态名 | 网页代码 | 程序在页面运行时自动加上或去掉 | **此刻处于什么状态**：哪个 TAB 被选中、哪个导航在当前屏、哪一行是银冠 | 用户每次操作时实时变化 |

例子（第 3 屏赛区切换）：
1. 设计稿：赛区按钮做成组件，有“选中 / 未选中”两个变体；
2. 生成网页：按钮带上 `data-region="cn"` 这类行为标记，两种变体的样子分别写进样式；
3. 用户点“国际服”：程序把 `is-active` 从“国服”按钮挪到“国际服”按钮，样式随之切换成选中图。

设计师**不用写** `is-`。它由设计稿里的变体（选中 / 未选中、普通 / 高亮）自动对应出来。

### 设计侧到底要做什么（用户总结，2026-11-12 确认）

2026-11-12 的分工讨论：设计侧提供语义和状态，程序生成 `data-*` 与 `is-`。2026-11-16 已明确这只是目标分工，现有动作／目标信息仍有缺口；补齐方式留 17.7b／F1，不能把以下示例当成“仅靠现有命名就已足够”的保证。原讨论补充两点：

1. 设计侧要做的完整清单：
   - 前缀：`sec/`、`fix/`、`img/`、`btn/`、`tab/`、`switch/` 等，以及新增的模块类型 `card/`、`list/` 等；
   - `@` 参数：点了干什么；
   - 变体：不同状态；
   - 接口标记：开关层、列表层、字段层（G6）；
   - 模块英文短词。
2. **变体的属性值要用规范里固定的词，机器才认得哪个是“选中”。** 现行规范已有的例子：
   - `dropmenu/` 开合：`on` / `off`（精确小写）；
   - `ind/` 指示器：`highlight` / `normal`；
   - 语言图：`lang` = `cn` / `tw` / `en` / `jp` / `kr`。

   写成“选中 / 未选中”“Property 1=激活”这类机器认不出来。TAB、按钮等其他状态的固定词，并入 F1 统一补齐。

### 接口标记和模块层级不是一回事（用户追问，2026-11-12）

用户问：接口标记是不是就是大模块、小模块、具体细节？答：**不是**，两者是两套标记，经常落在同一批图层上，但各管各的。

- **模块命名**（`panel/`、`card/`、`list/`、`row/`）回答“这是什么、怎么排”。每个模块都要有。
- **接口标记**回答“这块内容由后台控制吗”。只有后台能改的内容才标。

对照（第 5 屏晋级名单）：

| 图层 | 模块命名 | 接口标记 |
|---|---|---|
| 整屏 | `sec/5-晋级名单` | 无（这屏没有开关；第 4、6 屏才有） |
| 选手列表 | `list/player` | 列表层：`player_list` |
| 选手卡 | `card/player` | 无（重复项本身） |
| 名字文字 | 无（文字图层不改名） | 字段层：`user_name` |
| 头像 | `img/头像` | 字段层：`user_portrait` |
| 卡片底图 | `img/卡片底` | 无（固定素材） |

可见：有模块名、没有接口标记的（卡片底图）；没有模块名、有接口标记的（名字文字）；两者都有的（选手列表）。三种情况都存在。
