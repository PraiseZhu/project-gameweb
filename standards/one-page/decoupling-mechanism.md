# 怎样保证 A～H 各环节独立（待确认）

更新日期：2026-11-20。接 R221 解耦检查和 R222 职责清单，讨论用什么机制保证每个环节只做自己的事、做完交下一环。只是方案，不实施。

## 1. 六条机制

| 机制 | 做法 | 防止什么 |
|---|---|---|
| 固定交付物 | 每个环节的成果有固定的内容和格式，交出时生成版本号（按内容计算，内容一变版本号就变） | 下一环拿到的东西说不清是哪一版 |
| 进门检查 | 每个环节开始前先检查收到的东西：上一环是否已通过、格式是否完整、版本是否对得上。不满足就拒绝开工，退回上一环 | 拿着没通过或过期的成果继续做 |
| 只写自己的地方 | 每个环节只能写自己的输出位置，收到的东西只读。环节结束后核对输入的版本号，有变化就判这一环失败 | D/F 偷偷改页面、C 改交接包 |
| 单独可运行 | 每个环节都能单独运行：给一份合格输入，就能产出自己的成果。可以单独测试、单独替换 | 必须整条链一起跑才能验证 |
| 问题清单退回 | 不通过时，按统一格式写问题清单：哪里、什么问题、影响什么、应该退回哪个环节。环节之间不直接调用对方 | 一个环节越界替别人修 |
| 流程编排统一衔接 | 只有流程编排知道顺序：通过就进下一环，不通过就按问题清单退回；单语言时跳过 E/F；C↔D、E↔F 自动循环 | 环节自己判断下一步，顺序写散在各处 |

## 2. 统一的环节记录

每个环节结束都写一份同样格式的记录：

- 哪个环节、第几轮；
- 读了哪些输入，各自版本号；
- 交出什么成果，版本号；
- 结果：通过／不通过／停止（并写原因）；
- 问题清单（每条带退回环节）；
- 调用了哪些共用工具，工具版本和结果；
- 给开发的待办（B、C 填写）。

全程所有记录串起来，就能从最终包一路查回范围确认。

## 3. 9 个问题按这套机制怎么解决

| # | 问题 | 解决办法 |
|---|---|---|
| 1 | 没有统一交接格式 | 固定交付物 + 统一环节记录 |
| 2 | C/D 检查重叠，D 借用 C 的结果 | 检查是共用工具；C 跑自检，D 独立跑全套；D 要复用 C 的结果，必须自己核对页面版本和规则版本都一致 |
| 3 | D 自己修页面 | 只写自己的地方：D 只出问题清单，页面由 C 改；改完重新进 D |
| 4 | 改稿绕过 B | B 出变化交接包，C 只读这份；仍是点对点修改 |
| 5 | 基础语言没有入口 | A 一并确认基础语言，写进范围记录 |
| 6 | 译文没有入口 | B 把译文和外语素材收进交接包；缺件语言单独标出，补齐后 B 只为该语言补一版 |
| 7 | G 来源随语言数变化 | D、F 交出同一种“设计确认版”；G 只认这一种 |
| 8 | 开发待办没来源 | B、C 写进环节记录，H 汇总 |
| 9 | C 直接连 Figma | C 用共用导出工具按交接包记录的来源和版本取素材；稿件版本不一致就停，退回 B |

## 4. 自动循环什么时候停

C↔D、E↔F 自动循环时，建议：同一个问题连续两轮没修好，或者一轮下来问题数没有减少，就停下报告卡在哪里，不无限循环。

## 5. 需要用户确认

1. 是否采用上面六条机制和统一环节记录。
2. 基础语言由 A 确认；译文和外语素材由 B 收进交接包。
3. 自动循环的停止条件。

## 6. R224 修订：全套自动检查放在 C，D 不重跑

用户指出 C 通过后才轮到 D，D 不需要再跑一遍。修订为：

- C 做完页面后跑全套自动检查（原 D01～D13 和 C 的八项送验条件合并为一套），发现问题 C 自己修，直到全部通过，才交 D。自动循环在 C 内部进行，第 4 节的停止条件用于 C 内部。
- D 不重跑检查，只核对 C 的检查记录：检查项是否齐全、记录对应的是不是交来的这一版页面、用的是不是当前规则版本。对不上就退回 C。
- 核对通过后，D 交设计师在 QA 页面查看；意见交 C 修改，C 修改后复跑受影响的检查，D 再核对一次记录。设计师满意后，D 交出设计确认版。
- E 和 F 同理：E 跑全套语言检查并修完，F 只核对记录，再交设计师整组查看。
- 第 3 节问题 2 的解法相应改为：检查只在 C（和 E）跑一次，D（和 F）只核对记录，不重复检查。
