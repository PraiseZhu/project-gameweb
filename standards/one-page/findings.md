## 已知未决与依赖

- 模块身份、动作／目标、跨端对应、重复项、数据字段、动效设置和字体声明等，按完整标准第二篇中的 F／C／D 事项继续讨论。
- 原资料清单仍为四类：Onepage 完整 Skill 与实际依赖版本；实际复用资源；字段说明及 JSON 样例；已有制作／验收方法与技术要求。根据 R006／P007，流程不把它们作为整体硬前置；拿得到就吸收，拿不到就由 one-page 自建等价合同。原始资料说明保留为来源记录，不静默改写为“已收到”。
- 2026-11-18 已确认的等价性目标：设计侧页面在架构、规格、代码规范、逻辑四面与开发侧要求一致。标准真源是已定 HTML v1；开发样本或资料只是可选交叉证据，不是未知内部实现的必须复制对象。
- 来源文档中的“已有／还缺”是其记录时的快照。本轮未取得新材料，不能把链接可读写成资料已收齐。
- 像素阈值和画质检查方法尚待校准；原 6% 不是“94% 还原度”，不得写成新标准已确定的门槛。

## 不从现有事实推导的结论

- 不从用户要求落盘，推导为 Q001 已同意。
- 不从最终 HTML 必须静态 DOM，推导为生成器实现路线已经确定。
- 不从独立分组，推导为要复制、删除或接管现有项目。
- 不从文档检查通过，推导为页面、流程实现或正式服务通过。
- 不从可能拿不到开发 Skill，推导为成品标准失效或可以猜字段、补字体；也不推导为全部流程讨论都必须停止。
- 不从原资料缺失，推导为既有后台兼容性可保证或所有缺件均能独立复原。
- 不从“独立建设”推导为可以省略页面级字体、素材、端别、状态、交互目标或字段输入；缺这些事实仍必须停在受影响环节。

## 架构提案的人话版（待确认）

## 五条架构修正已确认

2026-11-18 用户确认五条修正作为架构基线：不提前回答 Q001；四面只做目标索引、A01～A12 负责验收；ready 清单与制作输入分开；缩范围只能改范围合同；流程能力证据与页面证据分账。

基于此，流程骨架为：范围合同 → ready 清单 → 制作输入合同 → 验收对象 → A01～A12 机器验收 → 程序白盒通过后的人工黑盒 → 问题回改 → 冻结交付包。该骨架不决定生成方式、工具、字段 schema 或旧项目迁移。


## 原固定链路已恢复

原链路不是被新架构替换，而是新架构下的实际主时序：出清单 → 制作静态页面 → 第一次黑盒验收 → 多语言与适配 → 第二次黑盒验收 → 最后压缩尺寸 → 最终包一致性复核。

五阶段／双线／五层用于规定每步的输入、责任、证据和回退；固定链路本身保留。



## 固定链路主流程

实际顺序是：范围确认 → 出 ready 清单 → 制作基础静态页面 → 机器白盒门 → 第一次黑盒 → 多语言与适配 → 机器白盒门 → 第二次黑盒 → 最终压缩尺寸 → 压缩后交付复核 → 冻结交付。两次机器门嵌在两次黑盒前，产品包与 QA 证据分开。



## 交互与动效阶段

交互和动效在“制作输入”阶段定义，在“基础静态页面制作”阶段实现；第一次黑盒查基础版本，第二次黑盒查多语言／适配后的完整版本。多语言与适配阶段只保留和适配既有行为，不重新猜交互或动效。



## 制作输入是独立步骤

ready 清单不是制作输入的全部。出清单后必须先整理制作输入，再制作基础静态页面；交互、动效、数据、字体、素材和缺口都在这里落地。制作输入不替代清单，也不形成第二份设计真源。



## 制作输入不是现成文件

当前只有 ready 清单和交接包，没有独立“制作输入”产物。ready 清单来自命名规范和设计稿；动作目标、数据字段、动效绑定等未在清单表达的内容，其正式来源尚未确定。后续必须先决定这些缺口由设计稿标记、项目资料、用户补充还是其他经确认的输入提供，不能让 agent 猜。



## 制作输入应随清单产出

标准已明确清单缺 G1～G6，且 G1/G2/G3 要写进命名规范定死；接口标记三层也已确定方向。制作输入不是外部开发资料或清单后的临时补表，而应是命名规范和设计稿共同产出的清单／handoff pack 字段。具体 schema、写法、解析和检查仍待流程阶段细化。



## 清单与制作输入合并产出

制作输入不是清单后的临时补充，而是命名规范／设计稿抽取出的 handoff pack 第二部分。交互／数据／结构关系进入设计声明并抽取；动效绑定单独建模，使用清单中的稳定身份，不启用未采用的 @motion。



## 首轮模块拆分

整体链路暂分 A～H 八块：范围合同、设计源抽取、制作输入 handoff、基础页面制作、第一次验收、多语言与适配、第二次验收、压缩／复核／冻结。每块通过版本化产物衔接，失败按模块边界回退。



## 整体架构基线确定

当前最终主链路为 A～H 八模块：范围合同 → 设计稿抽取与完整 handoff pack → 基础静态页面 → 第一次验收 → 多语言与适配 → 第二次验收 → 压缩与复核 → 冻结交付。B 同时产出设计清单真源与制作输入声明；D/F 都是机器白盒通过后人工黑盒；G/H 分开处理压缩复核与冻结交付。



## 模块 A：范围合同

范围合同在出清单前生成，来源是用户／任务范围决定，不是从设计稿画面猜。建议用固定范围确认对话收集语言、端别、屏／模块、功能、不做范围和缺失处理；确认后才进入 B 出清单。



## 固定链路 Skill 入口

新 one-page 流程继续采用旧 Gameweb 的固定链路 Skill：一个触发词启动，Skill 从 A 范围确认开始，依次编排 B～H；用户确认是 A 的硬闸，失败／缺口停在对应模块，不允许跳步、静默降级或直接进入做页。



## A 模块范围合同结构

A 需要锁四组信息：任务身份、交付范围、明确排除、停止／变更规则。auto-onepage 触发后先形成范围摘要，用户确认后生成 versioned scope contract，才进入 B。上下文可预填，但未回答不算同意。



## A 模块收窄为三项确认

A 只确认设计稿、实际语言数量／集合、单端／双端。模块、数据、交互、动效和页面结构由 B 从设计稿与命名规范／清单抽取；缺口在 B 停，不在 A 反复口头询问。每个设计稿都是新任务，scope contract 最小化。



## A 的交互建议：范围确认卡

A 不用大表，也不靠纯聊天。建议用三字段范围确认卡：Figma page URL、实际语言集合、PC／Mobile／双端。上下文可预填但必须用户确认；校验失败停在 A，成功后确认 scope contract 才进入 B。



## B 模块首轮结构

B 分四层：来源资格（B0）、设计真源抽取（B1）、制作输入声明抽取（B2）、校验与打包（B3）。handoff pack 分 meta、designTruth、productionInput、assets、validation 五区。B 不猜语义，unknown 和冲突带影响范围；通过 B 门后 C 才能消费。



## B0 增加 Skill 复用检查

现有 ews／Gameweb Skill 能复用就优先复用和改造，不默认从零搭建；复用检查是实现准备，不是 page 来源资格硬阻塞。复用旧项目能力需记录来源、版本和差异，维护归属不明时用适配层或交接路径，不静默改源文件。


## auto-one_page 全局复用前提

现有 ews／Gameweb Skill、模板、脚本和检查能力的复用优先级适用于 A～H 每个模块，不是 B0 专属。每个模块先盘点可复用能力，再决定复用、适配或自建；记录来源、版本和差异，不降低 HTML v1，也不静默覆盖其他项目的维护文件。


## B0 状态与证据

B0 建议使用 pass／fail／not_run／changed，n_a 不用于来源资格。检查 source-access、scope-match、ready-eligibility、design-set-identity、source-version 五项；每项带证据、原因、影响范围和下一步。B0 pass 只说明来源可进入抽取，不代表 handoff 已完整。



## B1 设计真源抽取

B1 输出 design-truth 主产物、实际平台切片、素材来源索引和 findings；只记录设计稿／命名规范事实，不抽动作、字段或动效语义。节点状态沿用 determined／unknown／skipped；证据绑定 scope、page 指纹、规范／工具版本、计数、来源路径和输出哈希。



## inventory／handoff 差异结论

现有 inventory/v2 + handoff/v1 已覆盖 B1 设计真源的大部分能力：节点、几何、角色、样式、切图、组件关系、端别配对、unknown／determined／skipped 和 fingerprint。主要缺口是 scopeRef 绑定和 B2 productionInput：模块语义、repeatGroup、dataMarks、interactionRelations、carousel／emptyState、语言字体声明、motionBindings、knownGaps 影响范围。


## 两轮验收架构调整

第一次验收前完成单语言页面的静态、交互、适配、动画和压缩；第二次验收前完成多语言页面的全部同类能力和压缩。C/E 是两次完整页面制作，D/F 是对应完整验收，G 只做最终包一致性复核，H 冻结交付。

## B2 首个缺口：G1 模块身份

现有 inventory 的 role/label 不等于模块语义。G1 需由命名规范或设计声明提供稳定模块根和模块类型，不能让 AI 看图猜；具体承载方式待讨论，暂不改现行字段。


## B1/B2 前置：命名侧能力对齐

现有命名规范不是所有制作语义的完整合同。B1/B2 实施前需先讨论命名、独立设计声明和清单派生的边界，再决定规范、解析器、inventory 和 handoff 的最小改造。



## 制作语义的承载原则

缺口不能全部靠 AI 判断，也不宜全部塞进图层名。推荐混合承载：命名规范负责节点本地结构事实；独立 relation／data／font／motion 声明负责跨节点关系和外部规则；AI 只解析、校验并生成 findings，最终统一进入 handoff pack。



## 核心决策：扩展命名规范

制作语义应新增到命名规范，作为唯一规则入口；不新增独立手工制作输入表。命名规范同时规定节点声明和跨节点关系声明，inventory 抽取为 productionInput，handoff 只装箱结果。



## 下一步：输入来源对账矩阵

为保证最终页面符合 HTML v1，先按 H/A/F/C/D 列出制作所需输入，标记当前来源和缺口，再决定哪些扩命名规范、哪些采用独立声明／项目资料，最后由 handoff 完整性门统一阻断缺失。
