## 13.1 图片格式、压缩与 SVG（要求已定；检测与校准归流程）

开发侧现状（2026-11-13 回读本机 `Downloads/ews2026`，提交 `39f9d71`）：

- 满铺背景使用 JPG，例如 `cn.html` 引用 `kv-pc.jpg`、`bg-qualifiers.jpg`。
- 透明图使用 PNG，例如 `slogan-cn.png`；`assets/manifest.json` 中该图的 `alphaRange` 为 `[0, 255]`。部分不透明小图也使用 PNG，例如 `official-button.png`。
- 线条、矢量图使用 SVG，例如 `bracket-merge.svg`。

用户已确认：**页面实际引用的位图统一从无损 PNG 源生成 WebP；SVG 保留为矢量交付。** JPG 不作为压缩中间格式或页面最终引用的位图格式；随包保留的原始／历史／备用文件按 13.2，不因格式不同自动删除。`img/`、`bg/`、`kv/` 仍只划定切图边界，不表达编码格式。

### 已核实的现状

- 当前 `ews2026` 样本的 README、manifest 和随包文件中，未找到成文的 WebP 编码参数或逐图压缩画质验收阈值。不能据此断言开发团队没有内部标准；已记入 R13 待要。
- Gameweb 伊瑟切图契约仍固定 `format: png`、`scale: 1`；`img/` 等前缀决定切图边界，不决定最终编码格式。
- 伊瑟切图阶段默认尝试转 WebP：编码器检测到 alpha 通道就用无损，否则 `quality: 90`；`method: 6`。当前检测的是通道存在，不是逐像素检查是否真的透明。
- 伊瑟 Pack 默认 `quality: 70`，大于 1024 字节的输入采用有损编码（`method: 4`），含透明通道的图和已经生成的 WebP 也可能再次编码；新文件不更小时会保留当前文件。因此现有实现并不保证最终所有位图都成为 WebP。
- Pack 当前检查编码结果、资源引用和整包体积；未见逐图 PNG 原图与最终 WebP 的 SSIM / 画质差异检查。现有停 1 像素门是页面对设计稿，差异比例阈值为 6%，不能直接当作压缩损伤的合格线。
- Pack 现有 15 MiB 整包预算及字体裁剪不直接沿用到新规范：第 11 项已定完整字库，整包预算按本项 13.3 的设计侧暂定建议记录；现有实现尚未调整。

依据：`standards/figma-naming/spec/inventory.mjs`；`skills/yise-web-ui/scripts/lib/encode-webp.{mjs,py}`；`skills/yise-web-ui/scripts/{figma-assets,pack-demo}.mjs`；`skills/yise-web-ui/docs/pack-skill.md`；`standards/stop1-figma-pixel/tool/src/stop1-figma-pixel-gate.mjs`。

### WebP 参数与画质要求（已定）

| 项目 | 规则 | 原样 / 优化 | 检查方式 | 信息来源 |
|---|---|---|---|---|
| 输入 | 每次由同一份无损 PNG 原图编码，不串联 JPG 或已压缩 WebP；PNG 原图作几何与画质证据，不作为页面实际引用的最终位图；随包历史素材按 13.2 | 优化 | 机器核对源图、源图哈希与编码记录 | 清单 + 源图 |
| 像素尺寸 | 不在压缩步骤缩放或裁切，宽高与导出框保持一致 | 沿用当前编码器保持尺寸的行为 | 机器：宽高差为 0 | 清单 + 源图 |
| 有实际透明像素 | 解码后任一 alpha 小于 255：`lossless: true, quality: 90, method: 6` | 已定；检测实际像素，不只看 PNG 是否带 alpha 通道 | 机器扫描 alpha | 源图 + 编码配置 |
| 全部不透明 | `lossless: false, quality: 90, method: 6`，从 PNG 直接生成 | 已定；不经过 JPG | 机器记录编码参数 | 源图 + 编码配置 |
| 透明与无损画质 | alpha 逐像素差为 0；可见像素 RGB 一致，alpha 为 0 的隐藏 RGB 不作误报；检查黑底、白底及页面实际底色下的边缘 | 已定 | 机器 + 人工 | 源图 / 最终图 |
| 有损画质 | 压缩后细线、Logo、渐变、颜色无可见劣化；与原图按相同尺寸、统一色彩解释核对。SSIM、PSNR 等检测工具和具体阈值由 Gameweb 流程确定，不作为本版未定条款 | 结果要求已定；检测方法归流程 | 逐图机器比较 + 实际显示尺寸人工核对；不以整屏平均分替代逐图检查 | 源图 / 最终图；校准样本归流程 |
| 最终交付 | 页面引用位图使用 WebP；文件能解码、尺寸及透明度正确、引用无缺失；换成最终压缩素材后重新验页面。原始／历史／备用文件按 13.2 保留 | 已定 | 机器 + 人工 | 最终包 |

`quality: 90` 不是“保留 90% 画质”，也不是“压到原体积 90%”；无损模式里的 quality 主要控制压缩工作量。`method` 是编码搜索强度，不是画质百分比。编码器版本与参数应一起记录。压缩率、单图上限以及 SSIM / PSNR 阈值不得凭空认定；具体检测、取样和校准归 Gameweb 流程，不再要求补齐这些参数才能定稿。整包上限按 13.3 的设计侧暂定建议。R13 是后续参考资料索引，不是定稿前置。

### SVG 格式依据（已确认原则；工具实现归流程）

Figma 中导入的 SVG 通常变成形状、矢量路径和组，不存在可靠的“子层名字叫 SVG 就是矢量图”规则。一个 `img/` 里同时有矢量线条和照片，整体仍含位图；导出成 `.svg` 也可能只是把位图包在 SVG 里。

已定：由程序检查**整个切图边界内完整、可见的绘制内容**，结果写入清单，做页照清单执行；不由 agent 逐图猜，也不新增格式前缀。

1. 排除已按第 0 项分离的网页文字，检查全部有效子层、组件实例内容及实际引用的绘制依赖。
2. 含图片填充或其他位图内容，分类为 `raster`，走 PNG → WebP。
3. 完全由允许的矢量形状、路径、描边和已验证的填充组成，才分类为 `vector`，进入 SVG 候选。当前允许范围为矢量路径、布尔运算、矩形、椭圆、多边形、星形、直线，以及只作容器的 frame / group / component / instance；渐变填充和描边可进入候选。
4. 存在 live `TEXT`、图片填充、复杂遮罩、滤镜、模糊、混合模式或其他未验证效果，分类为 `raster` 并记录原因；不能为了导 SVG 擅自拆开原有 `img/` 边界。
5. 结构或依赖无法完整读取时，格式判定为 `unknown`，清单 fail-visible，不能继续打 ready 包；不能把“读不到”当成“没有位图”。
6. SVG 候选从 Figma 直接导出，检查无 `<image>`、无外部依赖、导出框正确，再在相同尺寸下渲染并与 PNG 基准比较。画面不一致或验证失败时，退回 PNG → WebP；如果连 PNG 基准也无法建立，则停止报告。
7. `sliceExport` 仍可使用 PNG 作为源图和几何证据；最终 `manifest` 另记 `deliveryFormat: "webp" | "svg"`。具体工具改造属于后续流程阶段，本轮不改实现。

每个素材的追溯记录至少包含：`classification`（`raster` / `vector`）、`sourceFile`、`sourceSha256`、`deliveryFile`、`deliveryFormat`、`deliverySha256`、`width`、`height`；位图还要记录实际 alpha 判定和 `encoder`、`quality`、`lossless`、`method`。这样 `img/` 只表达边界，格式结果由机器证据决定。

## 13.2 未引用素材和历史素材（✅ 已定 2026-11-13：按开发侧保留）

开发侧做法是保留原始和历史素材：例如 PC 背景改成 JPG 后，原 PNG 仍留在 `assets/`。素材目录可以包含当前页面未引用的旧文件、重复格式文件和备用视频；不在交付前自动做引用闭包删除，也不因“未引用”把交付判红。

已定规则：

1. `assets/` 中的原始、历史、备用素材可以继续随交付目录保留。
2. 页面实际引用的图片、SVG、WebP、视频和字体必须存在；缺一项就失败。
3. `manifest.json` 记录交付目录内素材的来源节点、实例、尺寸、字节和校验值，以及 13.1 已定的 `classification`、`deliveryFormat` 等字段；工具如何生成这些字段留到流程阶段实现。
4. 不把“没有被当前页面引用”当成删除理由，也不由 agent 或脚本擅自清理历史素材。是否主动清理由后续明确的开发维护动作另行决定。

| # | 规则 | 原样 / 优化 | 检查方式 | 信息来源 |
|---|---|---|---|---|
| 13.2 | 保留原始和历史素材；页面引用必须存在；manifest 记录交付目录内素材的来源和校验值 | 原样 | 机器检查所有运行时引用可解析、文件存在、manifest 与交付目录一致；未引用文件不判红 | 开发侧 README、assets/manifest.json |

## 13.3 视频格式与体积上限（设计侧 Gameweb 优化建议，暂定 2026-11-13）

**开发侧未定：当前没有取得开发侧明确的视频格式、单视频上限和整包上限规范。以下由设计侧作为 Gameweb 优化建议暂时规定，不得标为开发侧现成标准，也不代表已经过实测校准。未来开发侧给出明确的正式规定和标准后，以其规范为准，更新本条并记录规范来源及变更。**

| # | 暂定规则 | 原样 / 优化 | 检查方式 | 信息来源 |
|---|---|---|---|---|
| 13.3a | 页面使用的背景视频采用 MP4 容器 + H.264/AVC 编码，不带音轨，启用 faststart | 设计侧 Gameweb 优化建议 | 机器检查容器、视频编码、音轨数量为 0、moov 位于媒体数据前；不是只把播放音量设为静音 | 用户 2026-11-13 确认；开发侧未定 |
| 13.3b | 页面使用的单个视频不超过 15 MB | 设计侧 Gameweb 优化建议 | 机器读取文件实际字节数，≤ 15,000,000 字节 | 用户 2026-11-13 确认；开发侧未定 |
| 13.3c | 实际交付整包不超过 120 MB | 设计侧 Gameweb 优化建议 | 机器累计交付目录内所有文件实际字节数，≤ 120,000,000 字节 | 用户 2026-11-13 确认；开发侧未定 |

计量与边界：

- 按本轮用户明确使用的 MB 计量：1 MB = 1,000,000 字节，不与旧 Pack 的 MiB 混用。
- “整包”按实际交付目录的全部文件计算，不按 ZIP 压缩后大小，也不只统计运行时引用资源。页面、脚本、样式、图片、视频、完整字体、manifest，以及按 13.2 保留并随包交付的历史或备用素材，均计入 120 MB；同一个文件在目录中只计一次，被多页引用不重复累计。
- 视频格式和 15 MB 单视频要求针对当前页面实际使用的视频；历史备用视频仍按 13.2 保留，并计入整包大小，不自动转码或删除。第 9.8 项跳转到外部网站播放的视频不作为本地文件计入。
- 第 6.4 项的分工不变：Gameweb 留背景视频接入口，开发负责接入；预留但尚未启用的入口不等于必须现在生成或压缩视频。
- 超限或格式不合要求时报告具体文件和差额，不标通过；不得为了达标擅自清理 13.2 保留的历史素材、裁剪第 11 项完整字库或降低已定画质。后续明确处理后重新检查。
- 本轮只记录规范，没有修改压缩脚本、已有素材或交付包；没有宣称当前开发侧样本已满足这些暂定上限。开发侧标准继续列入 R14 待要。
